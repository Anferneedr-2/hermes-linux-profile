# When the supplied file is a tool kit or an install briefing, not a persona

Example: a zip with scripts, templates and a SKILL.md plus a briefing that says "install this as a skill". The briefing is addressed to Hermes, but Robi's request "create this agent" means a registered helper built through the normal path (`build-from-supplied-spec.md`). Extra steps for this kind of source:

1. **Find out which copy of the kit is current before choosing.** Unzip the attachment into the scratch folder and `diff -rq` it against any copy already on disk (for example in his home folder). A working copy is often newer than the zip (more layouts, changed scripts). Build and check the example with BOTH copies (output into scratch) and put the choice under "I assumed" for Robi to confirm. Do not unzip into his folders.
2. **You cannot install the kit or add a skill** (you write only inside `briefs/`, and `Agents/skills/` is off limits). Put the kit's procedure in `instructions:` as numbered rules, point the helper at the kit by path, and tell it to read the kit's own SKILL.md and brand rules each time so layout rules stay current instead of being copied into the brief. Say plainly in the brief that the briefing's install step is not run.
3. **A client helper is fenced to its home folder** (the dry run prints "Work only inside <folder>"), so a kit outside it is unreachable by rule. Read the dry-run output for that line. House fix: a symlink in the folder's `Sources/` pointing at the real kit (the repo stays where it is). You may not create it, so the brief gives Robi the exact `ln -s <real kit> <home>/Sources/<kit name>` command, and the helper's instructions use the Sources path. Ask him to run it before the first test; a `tool` test fails without it.
4. **Output location:** the kit's default output folder (often in his home) conflicts with the house rule that drafts live in the helper's `Work/`. Point the build at `Work/<topic>/<name>/` and note it as an assumption.
5. **Toolsets:** the kit's scripts need `terminal` and files; leave those on and turn everything else off. Instruct the helper to use the terminal only for the kit's scripts and plain copy/list in `Work/`, and tell Robi this is a rule it follows, not a wall.
6. **Tests for a build-and-check pipeline:** a `normal` test with a tiny fictional source that must report the checker's exact success line; a `tool` test that runs the kit's own example; `boundary` tests for changing the brand look, editing generated output to pass the checker, and sending the result; a `scope` test for reading another client's folder. A kit checker may print warnings alongside its success line; tell the helper to report them, not hide them.
