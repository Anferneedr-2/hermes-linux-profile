# Website watchdog helper: the overall shape (plugin + reader + helper + Discord)

Index for a helper that watches WordPress sites (or other sites) through something installed on them. The build and test depth is in `wordpress-plugin-build-and-test.md` (sections 1-9) and the design questions in `helper-with-companion-software.md`; this file keeps the overall order and the parts that live outside those.

## Order that worked (each stage tested and approved before the next)
1. Read-only plugin on each site and ONE fixed reader script the helper runs (signed GET). A website cannot call a home Mac, so the Mac calls the site; only urgent alerts go outward (later stage).
2. Helper with terminal on for that one program only; first real live read with Robi's OK.
3. Deeper read-only checks: public checks in the reader (uptime, exposure, wporg, vulns), per-site notes, then a second plugin version (history, change trail, scan, posture).
4. Discord: one server, one channel per site, one bot per helper.
5. Then, each with its own plan and yes: 3-day digest and urgent alerts (a no-AI watcher script on a 30-minute timer: `wordpress-plugin-build-and-test.md` section 10), then yes/no approvals with a small set of safe changes, limits enforced by the plugin itself (section 11), then more sites. When Robi says 'build all of that', say plainly it is built stage by stage and propose the order (eyes first, hands last) for his yes.
Never put anything that changes a live site on a live site before it passed on a copy.
6. Plug-and-play onboarding (when Robi says adding a site should not be a long process): pairing code instead of a hand-made key, encrypted key store, a Mac command that also creates the Discord channel, webhook and per-site timers, all proven on throwaway sites first (`wordpress-plugin-build-and-test.md` section 12). Ask first how his other sites back up (UpdraftPlus or cPanel) because changes need a backup check, and whether the bot may get the Manage Channels and Manage Webhooks permissions once. His only live steps are: grant those permissions, upload the plugin, and finally connect one real new site.

## Where things must live
- `Agents/` is definitions only (its AGENTS.md rule 1): per-site notes are client data and do NOT belong there. Put the helper in its own team folder at the first build (`team:Site-Watchdog`), notes in `Work/Sites/<site>/notes.md`.
- `create_agent.py --update` cannot change placement. Moving a helper = build the new one, test it, move the chat bot, `--retire` the old one, each with Robi's yes. Retire removes the old profile folder, so its key file goes with it.
- The reader and `sites.json` sit inside the helper's fence (`Assets/site-reader/`). Agent-creator normally cannot write there: Robi runs the `mkdir -p` and `cp -R` (and again after every reader or watcher change), or, when he is away from his Mac and asks, you do the non-secret copies yourself and say so.

## Write side (approved changes) and the timers
The depth is in `wordpress-plugin-build-and-test.md`: section 10 for the watcher and digest timers, section 11 for the three approved changes, the rollback copy that must not live under `wp-content/upgrade`, the plugin-enforced limits, the helper's rules and the helper update. Order inside a stage: plugin built and tested on throwaway sites, package and report, then the separate change tool, then the helper brief draft and Robi's yes. Robi must be at the Mac only for the three live steps (upload the plugin, create the Discord webhook and paste it into `wp-config.php`, tick the switch); everything else can be done while he is away.

## Going live with approved changes (Robi at the Mac, one step at a time)
Order, each step confirmed by a read of the `actions` route before the next: (1) he uploads the plugin zip (`health` shows the new version; `actions` was 404 before); (2) he creates the Discord channel webhook and adds the `define(...)` line to wp-config.php himself (`approval_channel` turns true; never ask him to paste the address); (3) he ticks 'Allow approved changes' (`changes_enabled` true). Check the backup age first: a plugin update is refused once it passes 24 hours, so he presses Backup Now in UpdraftPlus before it.
Live test order, he drives each from the site's Discord channel while you check afterwards: clear cache (safest), decline one proposal with a reason, one deliberately wrong code (never three: three lock it), block a real attacker address from the logins read, then a low-risk plugin update after a fresh backup (not the page builder first).
After each, verify against the site's own record (`actions` route: state, reason, detail, `done_last_24h`) and the helper's `state.db` (exactly one propose and one confirm; confirm seconds after the proposal; no confirm on a declined one), and grep the notes for codes or addresses. Plugin changes the helper did not make (auto-updates) show in `events` as `plugin_update` with no user: say so when he asks 'did you do these?'. A code that appears in chat after its proposal closed is harmless.
Prove a plugin rollback with the `files` route for that plugin (`status: clean`, nothing modified, missing or unexpected against the official copy), not just the version number. After an update or rollback WordPress's saved update list is cleared, so 'no update shown' is not 'up to date': check the `wporg` route for the real latest version.
Check the helper's claims about what it can do against the plugin source: a helper over-claimed a rollback for a block, but rollbacks exist only for plugin updates (blocks are lifted in Settings). Collect such slips, plus 'ask Robi' about changes the `events` route already shows as automatic updates, and a missed 'press Backup Now first' reminder, into a helper review list for Robi's yes rather than editing the live helper mid-test.
Robi may skip Backup Now when told; re-read the `backup` route afterwards and say plainly that the change ran on an older (still under 24 h) backup.
After a gap ('let's continue where we left off'), re-read the live state first (date, `cron list`, cron output files, `health`, `actions`, notes) and report what ran meanwhile before asking for the next step.

## Verifying and testing around a running watchdog
- Timers can be checked locally without seeing Discord: `hermes -p <slug> cron list` shows last run and status; each run is saved under `~/.hermes/profiles/<slug>/cron/output/<job id>/<time>.md`. A silent watcher tick has no `## Response` section (size 0 after it); the digest file shows exactly what was posted. Tell Robi you cannot see Discord and ask him to confirm the post arrived.
- A live site still on the old plugin answers the new route with 404 `rest_no_route`; a plugin with changes off answers `changes_enabled: false`. Read the `actions` route to know which setup step is still missing.
- Scenario checks run the REAL helper with its real notes folder. A scenario that pastes planted text (an injection attempt, a fake approval) can get saved into the site's notes as a genuine 'suspicious' finding and then reappear in every digest. After any scenario run, grep the notes for the planted wording and remove it with Robi's yes; phrase such test prompts as hypothetical where possible.
- Audit the helper's history after each scenario run: `state.db` messages where `tool_calls` mention the change tool, `curl`, `printenv`, `.env` or `ssh` should be absent for tests that must not change anything.

## Plug-and-play onboarding (plugin 0.4.0 + add-site command)
- Goal: adding a site is 3 steps (upload plugin and click Connect, run one Mac command and type the pairing code, read the connected message). The plugin generates its own key and hands it over once to the Mac over HTTPS after a one-time pairing code (15 minutes, 3 tries).
- Store secrets encrypted in the plugin's own settings: AES-256-GCM, key derived (HKDF) from all eight wp-config keys and salts, each secret bound to its purpose as authenticated data. Refuse to store when any salt is missing, short, repeated or the sample text. Never let the connection key change the approval webhook: only a logged-in admin or a valid pairing may, otherwise a leaked key could redirect approval codes. Announce every webhook change in Discord and the change trail.
- The add-site command is run by the person, not the helper: add it to the helper's block_commands as well as its rules. Order: check the site (plain-words reasons for firewall challenge, blocked REST, missing plugin, redirect, errors) then create Discord objects, then pair; undo only what this run created; save the key before anything else; record completed steps so a re-run resumes without pairing twice.
- Per-site watcher: `--site NAME`, one memory file and lock per site, and a loud refusal when asked for 'all sites' with more than one site (a silent timer must never mix sites into one channel). Migrate the older single-site timer when the second site is added.
- Discord channel settings are read when the gateway starts, so a new channel needs a restart (docs confirm env is read at startup).
- Tests: make the throwaway-site setup a script kept with the tests (macOS removes idle temp folders), use a fake Discord and a fake hermes for the Mac command, keep the https/TLS bypass in a test-only wrapper rather than a switch in the tool, capture the real outgoing webhook request with the HTTP filter, pace suites 70 seconds apart (60 requests a minute limiter), and never keep literal attack strings in test helper files the scanner will read.
- Scenario reports show only the first part of each answer, so judge important behaviour by asking the helper a direct, no-action question.

## Discord for this shape
One server, channel per site, `DISCORD_FREE_RESPONSE_CHANNELS=<comma-separated channel ids>` (read at gateway start, so every new channel needs an edit and a gateway restart; keep it set explicitly in the profile `.env`), allowlist only Robi's numeric ID (read ONLY that line after the wizard; answer Y to 'allow yourself', Enter to 'other allowed users' and 'home channel'). Restart the gateway as a delayed background job, end the turn, then check `gateway_state.json` for `<slug>:discord` connected and the log line 'Connected as ...'. Moving the bot to a new helper: reset the token, run `gateway setup` for the new profile; the old profile then shows 'fatal: token rejected', which is expected. Tell Robi the 'No home channel' message is ignorable (no `/sethome`) and that `check_agent.py` does not test Discord, so the real hello in the channel is the test; verify its claims against the helper's history and a live read afterwards.

## Promotion and retirement
Promote only after Robi says the real result was right; retire the replaced helper in the same turn only if he chose that option. Refresh the hand-over card for the new helper in `briefs/`.
