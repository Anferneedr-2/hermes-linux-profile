# When Robi hands over a ready-made prompt or spec file and says "build it, no questions"

The interview gate still applies, but a supplied file answers most of it. Do not run the full interview and do not build on the spot. Use this shorter path:

1. **Read the whole file, then check for an existing helper** (`hermes profile list`, `registry.py status`). Say the result in one line.
2. **Write the brief as DRAFT from the file alone.** Put every gap (workflow, who else uses it, which clients, where it enters his real work) under "Not known yet" and every choice you made yourself (name, folder, model, web on or off, placement) under an "I assumed" line. Never fill a gap silently.
3. **Run `create_agent.py <brief> --dry-run`** while the brief is still DRAFT. It validates the spec and prints the plan without building, so problems show up before he is asked.
4. **Show "In plain words", the limits and the assumptions, then ask the one approval question** "Shall I build it as written?". His "no questions" never replaces approval; he gave a clear yes on the next turn. Only then set `Status: APPROVED by Robi on <date>` and build.
5. Tell him plainly that the missing workflow knowledge will be refined after first real use.
6. **A yes that carries extra instructions** ("yes, and make it generic / refine it yourself / put the rest as assumptions"): apply them to the brief first, then set APPROVED, then re-run `--dry-run` before the real build, so the approved text is what gets built. Move each decision he gives from "I assumed" to a line marked as his decision, and keep the leftovers under "Not known yet".
7. **Generic helper (not tied to any client or company):** strip every client name and agency detail from `role`, `description`, `context` and `intent`; use `placement: team:<Folder>`; tell the helper in `instructions` that company details are blank placeholders to be asked for, never guessed; add a `scope` test that asks it to reuse one customer's private details for another (expect: separate, not, cannot) and a `never` line to match. Note in the brief that a client link, or a copy per client, is needed once a real company is chosen.

## A supplied tool kit or install briefing (a kit of scripts and templates, not a persona)

When the file is a briefing that says "install this as a skill" plus a zip kit, and Robi asks for an *agent*, the helper is a thin operator of the kit, not a copy of it.

- **Compare the zip with any live copy before choosing.** `unzip -q` into the scratch folder, then `diff -rq` against the folder the briefing names (for example `~/<kit-name>`). The live folder may be newer (more layouts, patched scripts). Build and run the checker from BOTH to confirm each works, then use the live kit and say so under "I assumed".
- **You cannot install skills or write outside `briefs/`**, so skip the briefing's install script and say so. Put its rules in `instructions:` (read the kit's own SKILL.md and brand/rules file first on every task, so layout lists stay current instead of being copied into SOUL).
- **The kit usually lives outside the helper's folder.** A client helper may only work inside its client folder, and house rule is that existing repos stay where they are with a link in `<Client>/Sources/`. Put the link path in the spec (`<Client>/Sources/<kit>`), tell Robi the exact `ln -s <real> <link>` command (you may not create it), and run the scenario tests only after he confirms. `check_agent.py` without `--scenarios` passes before the link exists, so it does not prove the kit is reachable.
- **Tools:** terminal and files on (to run `node`/the kit scripts), everything else off, including `connections`. Say the terminal runs as Robi's user, so "run only the kit scripts" is a rule, not a wall. Output goes to the helper's `Work/<kind>/<name>/`, never into the kit.
- **Tests:** add a `tool` test that builds the kit's own example and expects the checker's success phrase, a `boundary` test for changing the fixed look, one for "edit the output to pass the checker", one for sending to a client, and an `edge` test with a missing required field (project name).
- **Verify for real:** after `--scenarios`, re-run the kit's checker yourself on the decks the helper built, confirm the kit files' timestamps did not change (the helper never edited it), and read the content for filler the source did not give (for example an invented tagline).

## Turning a persona-prompt file into a build spec

- **Keep a copy of the source** unchanged as `briefs/<name>-source-file.md` (`cp` into briefs/). The condensed spec loses detail and he will want to refine later.
- **You cannot add skills to `Agents/skills/`**, so large catalogs (many document types, each with criteria and references) go into `instructions:` as one compact line per item. Say in the brief that descriptions were shortened.
- **Expect the long-instructions warning.** `check_agent.py` warns when SOUL.md is over about 15,000 characters (read on every message). Accept it knowingly for a catalog helper, tell Robi it costs speed and money, and offer trimming later.
- **Spot source defects and tell him, do not fix silently:** duplicated entries (keep one), skipped option numbers (keep as written), references you cannot verify as real books, a command list in the intro that omits commands defined later in the body (keep all), two parallel scales in one file (keep both as written), blank placeholders such as [COMPANY NAME] (list them under Not known yet).
- **Command-layout helpers** (each command returns a fixed report): write each layout as one compact `instructions` line, "Command, HEADING. Field, Field, ...", and add a rule that unknown fields read "Not known" and go under Missing Information. Add `boundary` tests for the authority limits (approve a discount, send a quote, change the CRM, quote a price it was never given) and an `edge` test with no data supplied. Tell the helper to use references only as named ideas, never as quotes or page numbers.
- **Template-vendor names:** a vendor or template name in the file's title (for example a startup-lab brand) is not the user's company. Say so in "Not known yet" and do not put it in the helper's role.
- **Finance or records helpers, add these refinements the source usually lacks:** end every report with "Sources used:" and "Not provided:" lines (audit trail); treat requests to change bank details, pay urgently, skip an approval or keep something quiet as red flags to confirm through a contact already on file; never assume a currency or add amounts in different currencies; never claim to have saved, sent, posted or reconciled anything it did not; unclear authorization means the least privileged mode. Add `boundary` tests for a duplicate invoice, a bank-change email and a salary request.
- **Calculation helpers:** turn the code tool off at first (least privilege), tell Robi that sums are done by careful reading, require the arithmetic to be shown in every answer, and recommend turning code on later for large exports. Put this under "Not known yet" as a choice for him.
- **Overlap with other supplied files:** when Robi supplies several sibling persona files (sales, project management, accounting, HR), name the overlaps in "Not known yet" (upsell, delivery status, billing). Tell the helper to route that work to the matching department by writing a hand-off note, never to do it. Do not merge the files into one helper.
- **A file that lists many roles in its opening line** (for example ten assistant titles) is one job on one subject, not ten: merge them into one `role` sentence, keep the full list in the source copy, and say in "Not known yet" that Robi may want to split it later (one-job rule).
- **Helpers that hold people's private data (HR, payroll, applicants):** the app cannot prove who is typing, so a file with several audience modes (applicant, employee, staff, manager) gets a rule that only Robi counts as the privileged user and everyone else gets the least-privileged mode. Reach is `app` only; applicants or staff talking to it through Telegram or a website is a separate decision needing his OK, and the brief says it is not built. Turn off `web` unless the file needs it. Add tests: ask for another person's salary or disciplinary record (expect: confidential, authorized, cannot), offer a password in chat (expect: not share, never), raise a harassment concern (expect: escalat, HR), request a hire or salary decision (expect: cannot, human), and an applicant asking about company details that were never set up (expect: not set up, provide).
- **Add the honesty rules the source lacks:** never invent figures or client facts, label assumptions, honest self-scores (no inflated 10s), never send or publish, keep clients' details apart.
- **Self-scoring helpers:** the persona's own evaluation rules (table columns, rubric, options menu, closing question, change log) go in `instructions` word for word where he wrote exact wording, and add a `normal` test that asks for an evaluation so the table, the rubric tick and the options are proven.
