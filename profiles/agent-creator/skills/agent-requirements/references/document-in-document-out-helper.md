# Helper that turns one document into another (report to invoice, notes to summary, sheet to letter)

Use when the helper's whole job is to read a source document and fill a fixed template. Simple-sounding jobs like this hide their real rules in the samples, so get the samples before designing anything.

## 1. Get the samples early (interview stage)

Ask for, in this order: one real **input** document, one finished **output** the person is happy with (it doubles as the template). Do not rely on the person's description of the mapping alone.

Read and look at every attachment yourself:
- Text: `read_file` on the PDF (extracts the text layer).
- Layout: `pdftoppm -r 80 -png file.pdf out` into the scratch folder, then `vision_analyze` the PNG (header, columns, totals block, footer, colours, payment/notes block).
- Hidden content: `pdfimages -list file.pdf`. Pages that are only images (screenshots, scanned tables) have no text layer, so data that lives there cannot be read by a text-only helper. Render those pages and read them with vision before deciding whether the helper can use them.
- Producer and title (`pdfinfo`) tell you whether a sample came from a word processor print or a proper export; a print-to-PDF copy may have broken line wraps.

## 2. Compare the person's description with the samples

The description is usually the clean version; the real input is messier. Check each point and show differences in one plain line before moving on:
- Does the output show something the person did not mention (headings, 0.00 instead of "-", notes, totals, payment block)? Ask which is right; two samples may disagree, and the person may say which is the correct one.
- Does the real input have the granularity the output needs (one row per item with its own number)? Grouped rows, "Included" placeholders or numbers that exist only in pictures mean the output cannot be built the way the earlier sample was. Offer the real options (use the rows as written, or pull the detail from the pictures) and let the person choose; do not pick for them.
- Does the input already contain header facts (person name, role, period, project, total hours)? Then the helper reads them from the report instead of asking each time. Confirm each one by name.
- When two samples share an identifier (same invoice number for two different people), ask how it is assigned and who owns the counter, and what the next value is.

## 3. Settle these rows for the brief

- Field-by-field mapping: output column, where it comes from, what is shown when the source says "Included" or is empty (use the person's exact symbol, e.g. "-").
- Fixed facts per person or entity (role line, fixed amount, payment details): where they live, who keeps them current, and that the helper must never invent or guess one. Payment details are private data: they live in the helper's own client or team folder, never in the Agents folder, and are never printed in test reports beyond what the person approves.
- Numbering: per person or global, next value, who confirms it.
- Dates: which one is the invoice/issue date, how the period is derived (from the report's own cutoff dates).
- Totals: copied from the report or recomputed; if recomputed, the helper must show the sum and flag any mismatch against the report's own total.
- Output name pattern and where it is saved. Saving to a shared drive (Google Drive and similar) is an outside-tool connection and needs the person's separate OK; start with the helper writing the file to its own Work folder and the person uploading it. If the person wants it saved straight to the drive, find out what the Mac really offers before promising a method: `manage_connections` status (a hosted connector for the drive may not exist), `ls /Applications | grep -i -E 'drive|google'`, `which gws rclone`. Then give two plain options and recommend the simpler: (1) the drive's desktop app, which shows the drive as a normal folder, so the helper just saves the PDF there and no key is shared (a client or team helper works only in its own folder, so the drive folder is reached through a link that Robi creates; give him the exact `ln -s` command); (2) a direct Google sign-in through the `google-workspace` skill, which has many more setup steps and, as shipped, asks for the full `drive` scope (read, change, delete and share everything in the signed-in account; it cannot be narrowed to one folder, and the skill is not in `Agents/skills`, so it needs the governance review before a helper may use it). Say this plainly when he picks option 2. If he wants access limited to ONE folder, offer a Google service account (a "robot account"): he creates it, shares only that folder with it and keeps the key file himself. It can normally write only into a **Shared Drive** folder, not a personal My Drive one, so ask which of the two the folder is in, and prove it with a real test upload before promising it. Do not offer an agentic browser that reuses his logged-in Chrome (such as ego lite): the helper would inherit every login he has, which is wider than any of the options above. Install, sign-in and folder choice are Robi's steps after the build, each with his separate OK, and the brief must name the exact target folder. Never install or connect anything during the interview.
- Approval: the helper makes a draft, the person checks it, nothing is sent or filed to a client without a yes.

## 4. Tests to put in the brief

- `normal`: the real input sample from the interview, expected output rows and totals worked out by hand first (add the times yourself, check the helper's arithmetic).
- `edge`: a report with a row whose time is "Included" or empty, or a name not in the list of people.
- `boundary`: missing pay or payment details for the person, a request to save or send the file to someone. Required phrase such as "I do not have that data" so the word check works.
- After the helper produces a file, render it back to PNG and compare it with the template visually, and read the PDF text to check every number.
- Test inputs must use a fictional person from a template people file, and each scenario its own period and number, because earlier test drafts stay in the helper's `Work/` and a later run may find and mention them. Tell Robi the leftovers exist; you may not delete them.

## 5. Make the layout a fixed program, not the helper's drawing

If the helper drew every PDF itself, small differences would creep in between invoices. Instead write a small generator and let the helper only read, fill, run and check.

1. Write `briefs/<slug>-maker.py` (you may write in `briefs/` only; there is precedent for scripts there). Input is one JSON file; output is the PDF. Copy the sample's layout (`pdftotext -bbox-layout` gives exact positions, `pdffonts` the fonts, vision the colours). Embed a real TTF (on macOS `/System/Library/Fonts/Supplemental/Arial.ttf` and `Arial Bold.ttf`) with `registerFontFamily`; the built-in Helvetica has no real bold in the viewer.
2. Make the program refuse, not guess: print `STOP: ...` and exit 2 when a field is missing, a placeholder amount is 0, or the rows do not add up to the report's own total, and write no file. Give the program `--schema` (prints an example JSON), `--check-only` (validates, writes nothing) and `--out`; refuse to overwrite an existing file, reject a value that looks like a password, and require every required section to hold at least one item (a gap is an item with a missing status, not an empty list). Print `OK <path> ...` only after writing the PDF. Test the good path, a wrong total and a missing field yourself in the scratch folder, then render the PDF to PNG and look at it (one page, nothing cut, totals aligned).
3. Write a fictional test JSON and a TEMPLATE people file (fake data only) next to it in `briefs/`. The brief gives Robi the exact `mkdir` and `cp` commands to put the program, the test JSON and the people file in the helper's own folder (`Assets/<tool>/` and `Data/`, `chmod 600` on the people file); confirm with `ls -la` and `cmp` before the scenario run. A `tool` test then runs the program's `--check-only` on the test JSON.
4. The helper's rules: build `input.json` in its own `Work/` folder, run the program with `/usr/bin/python3`, treat only a first line starting with `OK` as success, show STOP lines as they are, read the PDF back and compare it with the JSON, and ask for approval before filing. Real PDF text extraction breaks words and times (a stray space inside a word or in `23:10:3 4`); allow it to repair only stray spaces and to list each repair. `read_file` can also jumble table columns or scramble a cell into letters, and then a status word such as "Included" gets read as the hours. Make the helper read the report two ways, `read_file` and `/usr/local/bin/pdftotext -layout "<path>" -` (read only; its terminal rule must allow this command), take every table cell from the layout copy, say which reader it used, and take hours only from the Time spent column. If a cell is still unreadable it asks instead of guessing. The arithmetic check catches a broken number; when it stops a run, first read the report with `pdftotext -layout` yourself to see whether the helper misread the table or the report itself disagrees with itself.
5. Real people data (names, pay, bank or wallet details): never write it into `briefs/`, the registry or a test report. If Robi pastes it in chat, normalise it to one format, give it back as a paste-ready block for him to put in the people file himself, leave out anything that is not payment data (old invoice references, codes the invoices do not use) and say what was left out, and use a safe placeholder (`fixed_amount: 0`, `FILL IN`) for what he did not give so the program's STOP prevents a wrong invoice. Name matching is by the name in the report, so tell him to check each name against the report, not the account holder's name. When a real report's name differs from the file's (a short name against a long one), the helper must stop with a fixed phrase and not guess. Ask Robi whether it is the same person and which name the invoice header should show. Because you may not edit the file, give him one command that changes only that line (`sed -i '' 's/^  - name: <old>$/  - name: <new>/' <people file>`), leave the account-holder name as the bank shows it, and verify with the script in step 6.
   - Copy every number from Robi's own message, never from an earlier PDF extract: sample PDFs often show masked values (for example a phone number with asterisks), and a masked value copied into the block makes every invoice for that person wrong. Re-read the finished block for asterisks before sending it.
   - When he asks you to enter it for him (you may not write outside `briefs/`), do not repeat the field-by-field form. Give ONE complete file, every person filled in, including the fake test person, with three steps: run `open -e <people file>` (opens it as plain text), Cmd+A then Cmd+V to replace everything, Cmd+S. Ask for missing facts (pay, role line) one question at a time first, so nothing has to be filled in by hand afterwards.
6. After he saves it, verify the file yourself with a short script that prints only names, role lines, pay, next number, block and line counts, and whether any account value contains `*` or has too few digits. Never print the account numbers. Also check `ls -l` shows permission 600.
7. First real run: start the helper with `-z "Real task, not a test. ... <attachment path>"` in the background, then check the PDF against the report yourself (`pdftotext -layout`, the helper's `input.json`, a rendered PNG, the people file counter unchanged). The one-shot run ends at "Do you approve?", and a later "approved" arrives in a new session with no memory of the draft. So when Robi approves, pass the helper the invoice number and the exact draft path in the same message, and have its instructions treat that path as the thing being approved. Afterwards confirm the file is in `Deliverables/` and the counter moved by one. Run approvals one at a time, never in parallel: each edits the same people file and parallel runs can overwrite each other's counter line (drafts may run in parallel). Verify the Drive copy by comparing the Drive file's `md5Checksum` with the local file's md5, and re-check every person's counter.
   - Your own chat output may come back with phone-like account numbers masked (`+639****2790`) even when you typed the full digits. After sending a block, tell him to compare that line with his own message, and verify by script that no account value contains `*`.
8. Saving to a shared drive as stage 2 (after promotion, with his separate OK): write `briefs/<slug>-drive-upload.py` the same way as the invoice program. It takes `--pdf`, `--folder`, `--check-only` and `--selftest`; it accepts only a fixed folder-name pattern (for example `Invoices - 26 Oct - 10 Nov 2026`) and a fixed file-name pattern, finds or creates that ONE sub-folder inside the target folder, uploads ONE PDF, and has no delete, share or overwrite (it stops if the name already exists). File and folder names use plain letters only: an accented name such as Quiñones fails the name rule, so the helper writes Quinones in file and folder names while the invoice itself keeps the accent. The helper also reports the `link=` the program prints. It reads the robot account key from the helper's own `Data/` or an env var and never contains a key. It refuses with `STOP` if the target folder has no `driveId` (not a Shared Drive). Test the name rules and the missing-key stop yourself; the real Google calls can only be tested after he creates the robot account (one small step at a time: Cloud project, enable the Drive API, service account, key file into `Data/`, share only the target folder with the robot's email). Then write a v2 draft brief with the new rules and run `--update` only after his new approval.
