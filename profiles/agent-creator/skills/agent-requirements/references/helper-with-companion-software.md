# Helper that needs companion software (plugin, script, service)

Use when the need is "a plugin / app / service that does X" and Robi expects a Hermes helper to be its brain (example: a WordPress site watchdog plugin run from Hermes on his Mac). Two separate things get built: the **helper** (a Hermes profile, built by `create_agent.py`) and the **companion software** (code; agent-creator has no folder for it outside `briefs/`, so it is written, tested and zipped there once the design is approved; see `wordpress-plugin-build-and-test.md`).

## 1. Say the split out loud, early
- Tell Robi in one plain line: the brain is the helper; the hands are the companion software; they are built in separate steps, each with its own approval.
- Never say "the plugin is built" after `create_agent.py`. A passing `check_agent.py` proves only the brain answers and holds back correctly. Say what it still cannot do (no site connection, no chat link, no timer, no backup tool).
- The helper's SOUL text must not describe the companion as installed. Write it as "not yet connected" with a fixed phrase for when no data exists, so test answers admit the gap instead of inventing results.

## 2. Interview questions that decide the design (one at a time)
1. **Who can call whom?** A Mac or home machine cannot be reached from the internet. Default: the helper polls the companion on a schedule (outbound only); the companion pushes only urgent alerts straight to the chat tool. Ask whether the Mac is always on, because every scheduled check depends on it.
2. **Where do safety rules live?** Put them inside the companion (refuse without a fresh backup, refuse outside the allowed list, one-time approval code per risky action), not only in the helper, so a helper mistake cannot bypass them.
3. **Backups.** For big or data-heavy targets prefer an existing, trusted backup tool and refuse to change anything unless it reports a fresh success. Ask which tool; each needs a small adapter.
4. **Mode per target.** Let Robi set a per-target mode at install (for example Simple vs Careful) with the cautious one as default; the software never guesses.
5. **Auto vs ask line.** Offer a concrete starting rule (auto: small patches, security patches, cache clear, block attacker; ask: core, big jumps, themes, deletions; careful targets ask for everything but blocking and cache) and let him adjust.
6. **Secrets.** Each target gets its own key; Robi places it and the chat webhook himself; the companion stores only a fingerprint; AI keys never live in the companion.
7. **How deeply must it know the target?** If Robi wants it to "know the whole site like it built it", propose: the companion sends a read-only copy of the target's OWN code, the helper studies it and keeps a per-target notes file (outside `Agents/`), third-party parts are compared with their official copies instead of read line by line. Say plainly that understanding code means it is sent to the AI provider, name what is never sent (database contents, customer data, passwords, keys, config files holding secrets), and get his explicit OK. This can contradict an earlier "nothing leaves my Mac" answer, so point out the conflict.
8. **Third-party tools it relies on** (a backup plugin, a feed of known weaknesses). Before promising an adapter, check the tool's real documentation: a free edition may not let other software read its status or start a job. Record it as an Unknown until checked.

## 3. Write the design as a separate file
Save `briefs/<name>-design.md` (status DRAFT, "design only, no code"): plain words, Robi's decisions in a numbered list, the pieces (read, alert, act), safety rules built into the software, build stages (read-only first, then alerts, then safe auto-fixes, then approved changes), tests in words, Unknowns, and the list of things needing a separate OK. Offer to write the code here, in `briefs/<name>/`, and say plainly what you can and cannot test. Do not push Claude Code or a separate coder: Robi rejected that. Write only the approved stage, never before the design is approved.

## 4. Pitfalls
- A scenario run that fails with a billing or credits error from a fallback provider proves nothing about the helper. Report it plainly, re-run when access is back, and read the real answers afterwards.
- First tests go on a test site or sandbox, never a live client system. Ask whether one exists. If Robi only has a live one, allow only the read-only stage there, and only with: a fresh backup he takes himself, he installs and activates it himself, a one-click switch-off, and the safest mode set. Nothing that changes the target goes live until it has passed on a copy. Confirm the target is a simple, not a data-heavy, one.
- Approve the design for the first stage only, and write that in its Status line ("APPROVED for STAGE 1 ONLY; later stages need an updated design and a new yes"). Robi's "yes" to a plain-words summary is not approval to build the helper: ask "Shall I build it as written?" and wait before setting APPROVED on the helper brief.
- Settle the split (section 1) before writing the helper's brief, not after the helper is built; otherwise the helper is built first and the real deliverable (the software) is still undesigned.
- Decide the helper's folder at its FIRST build. `Agents/` holds definitions only (its AGENTS.md forbids client data), so a helper that will keep per-site notes or other client data belongs in its own team folder from the start. `create_agent.py --update` cannot change placement (it stops with 'placement cannot change on update'); the only route is to build a new helper under a new name in the new folder, test it from the terminal, move the chat link, then retire the old one, each with Robi's yes. Costs to tell him up front: the key line is added again to the new profile's `.env`, the reader folder is copied over, and a Discord bot token can live in only one profile, so he resets the token and runs `gateway setup` for the new profile after it passes. The old helper keeps working until then.
- When Robi says 'build all of that' for several later stages, do not agree to build them at once. Offer an ordered list in which every stage is planned, tested and approved on its own, with timers, outside messages and every site-changing action each needing a separate yes, and with changes last so the helper's read-only eyes are trusted first. Ask only whether the order is right.
- When Robi says two things 'should merge' (the helper and the plugin, or the old and new helper), restate it as one assumption (one helper replaces the old one; the plugin keeps its name) and get a yes before building.
