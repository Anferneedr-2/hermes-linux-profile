# Building and testing a WordPress companion plugin inside briefs/

Use after the design (`helper-with-companion-software.md`) is approved for a stage and Robi wants the plugin written here. He rejected handing the code to Claude Code or another coder ("why do we need that"), so offer to write it yourself in `briefs/`, say plainly what you can and cannot test, and do it. Only the approved stage is written.

## 1. Layout and order
`briefs/<plugin>/` (main file with settings screen, `includes/class-*-core.php` pure logic with NO WordPress calls, `includes/class-*-api.php` WordPress-bound routes, `uninstall.php` that removes only the plugin's own data), `briefs/<plugin>-tests/` (unit tests, live test client), `briefs/<plugin>-<version>.zip`, `briefs/<plugin>-<version>-test-report.md`. Order: code, `php -l` every file, unit tests, live tests, zip, report, install steps. Keep PHP 7.4-safe syntax (no `match`, union types, `?->`). Keep pure logic separate so it can be tested without WordPress.

## 2. Rules for a read-only plugin that Hermes polls
- GET routes only (`WP_REST_Server::READABLE`); every route uses one shared `permission_callback` gate, never `__return_true`.
- Gate order: switched-off option, HTTPS, rate limit (not logged, so floods cannot fill the log), HMAC-SHA256 over timestamp, method, route and sorted query (drop `rest_route`), 5-minute window, replay guard (transient keyed by the signature), constant-time compare (`hash_equals`). Refusals return one generic message; the real reason goes only in the plugin's own log.
- The key is a constant in `wp-config.php` (at least 32 characters). Never a screen, a log or a response, and not plain text in the database. Robi makes it himself (`openssl rand -hex 32`) and it never enters chat. (Once he asks for plug-and-play setup, the key moves into an encrypted store with pairing: section 12. The wp-config constant keeps working and wins.)
- Mode option (Simple/Careful) defaults to the cautious one. A switch-off option makes every route refuse at once.
- Code and log sharing: realpath must stay inside the allowed roots (no symlink following, no `../`), extension allow-list, never `wp-config.php`, `.env*`, keys or dumps, size cap, and blank out secret-looking values and lines before sending. User list shows administrators only, no emails or hashes.
- Third-party tool status (for example a backup plugin) is read from that tool's saved record; if it cannot be read, report `unknown`, never `ok`. Check the real format against the real tool before trusting it.
- A read route may write only the plugin's own data (log, baseline, counters). Say so in the report.

## 3. Tests that gave real evidence
1. `php -l` on every file; a unit test script on the pure class using a temp folder (signatures, replay window, secret removal from logs and code, file fence, symlink and `../` escape, baseline diff, status parsing).
2. Live tests on throwaway WordPress with the Playground CLI (Node needed; EBADENGINE warnings are harmless). Run each instance in the background and wait for `Ready!` in its log:
   `npx --yes @wp-playground/cli@latest server --port=9400 --blueprint=<bp.json> --mount=<plugin dir>:/wordpress/wp-content/plugins/<slug> --mount=<host mu dir>:/wordpress/wp-content/mu-plugins`
   Blueprint steps that worked: `defineWpConfigConsts` (test key, `WP_DEBUG_LOG`), `writeFile` (a planted `debug.log` with fake secrets; tamper files in `wp-includes` and `wp-admin`), `setSiteOptions` (fake backup record, mode, switch), `activatePlugin`. Call routes as `/?rest_route=/<ns>/v1/<route>`.
3. Playground is plain HTTP, SQLite and PHP 8.3 whatever `preferredVersions` says. Force HTTPS with a test-only mu-plugin (`$_SERVER['HTTPS']='on';`); an instance without it proves the HTTPS refusal.
4. Start one instance per start-state: clean, tampered core, no-HTTPS, switched-off. A first call that creates a baseline cannot be re-run on the same instance, so restart it (`pkill -f 'port=<n>'`) before a re-run; at the end `pkill -f wp-playground`.
5. Read-only proof: a test-only mu-plugin prints, on `?sw_dump=1`, an md5 per option (skip transients, the plugin's own options, `cron`, `recently_activated`) plus fingerprints of posts, users and usermeta (skip the plugin's own meta). Compare before and after the full run.
6. Test client in stdlib Python run with `/usr/bin/python3` and a throwaway test key; the real key never goes in any file. Cover: no, wrong, old, other-key and replayed signatures; POST, PUT, DELETE, PATCH; path-escape attempts for the code route; the key absent from every answer; planted secrets removed; anonymous visitors cannot see the settings page; request flood answers 429.
7. Client pitfalls: macOS has no `timeout` command; `urllib` follows redirects, which hid the login redirect (use an opener that does not follow and read `Location`); store checks as `bool(...)` or the final `sum()` fails on list values.

## 4. What the report must say it did not prove
Not run on MySQL, older PHP, or a real host (panels, caches and firewalls can block REST calls or hide HTTPS); the third-party backup plugin's real record format if it was faked; the Hermes side; the settings page as a logged-in admin; no outside security review (recommend one before use on important client sites).

## 6. Next piece: the Hermes-side reader
A fixed signed-request script the helper runs; the helper never sees the key. It needs the helper's `terminal` toolset on, narrowly: tell Robi this is a rule the helper follows, not a wall, and get his OK before changing the helper through an updated brief (draft `<name>-v2-draft.md`, dry run with `--dry-run --update`, his yes, archive and `mv`, then `--update --approved --smoke`).

**The script** (`briefs/<reader>/sw_read.py` plus `sites.json`, stdlib Python, run with `/usr/bin/python3`):
- Arguments `--list` or `--site NAME --route ROUTE [--param k=v]`. Allow-list the routes and the parameter names; GET only; refuse any site not in `sites.json`; refuse non-HTTPS except `127.0.0.1`/`localhost` for tests. Try `/wp-json/<ns>/<route>` first and fall back to `/?rest_route=` on 404 (plain permalinks). Send a `User-Agent`.
- `sites.json` holds names, URLs, the NAME of the key variable and the mode label; no secrets. The plugin's own reported mode wins over the label; a mismatch means treat the site as the cautious mode.
- The key is read from the helper's private `.env` (variable per site, for example `SW_KEY_<SITE>`); the script refuses a file readable by others, prints `STOP: ...` with exit 2 for every setup problem, and replaces the key with `[key]` in anything it prints. Test-only overrides come from environment variables (`SW_ENV_FILE`, `SW_SITES`).
- Test it against a Playground instance with a throwaway key: list, a good read, wrong key (plugin refuses with 401), missing key variable, unknown site, bad route, bad parameter, plain-HTTP site, key file mode 644, and a grep proving the key never appears in output.

**The helper's rules** (build spec): terminal for that one program only; routes and parameters named; never open, print or search any `.env` or the environment; never edit the script or the site list; exact phrases for 'I can only read in this stage', 'That site is not in my list, ask Robi to add it', 'I cannot show keys; you keep them'; a freshness rule for the backup read ('No fresh backup, I would not change anything on this site' when status is not ok or older than 24 hours; the 24 is an assumption to tell Robi). `block_commands` that passed: sudo, rm, curl, wget, ssh, scp, printenv, .env, chmod, mv. Tests: intro, one live `tool` read, a backup read, two change requests (`boundary`), an unlisted site (`edge` with the fixed phrase), a key request (`boundary`), a core-update advice question, and a not-built-yet (digest, alerts) question.

**Robi places the key** (one message per step): `open -e ~/.hermes/profiles/<slug>/.env`, add `SW_KEY_<SITE>=<key>` as a new last line with no quotes or spaces, save, then `chmod 600` that file. Check it without reading the value: `stat -f %Lp` (600), `grep -c '^SW_KEY_<SITE>='` (1), and `awk` printing only the value's length (64) and whether quotes or spaces surround it. A first live read that returns real data proves the two keys match.

**Order on the live site** (each read needs Robi's OK, read-only, says what it reads): health first, then the scenario run (its `tool` and backup tests are live reads: say so and ask before running), then read the helper's `state.db` for the reader calls and for any `.env` or `printenv` call (must be 0).

**Verify a user's stated fact with the tool.** Robi said the backup was from today; the real record said 102 hours old. Do not pick a side: say the two readings differ, then run the test that tells them apart (he presses Backup Now, you read again; under an hour proves the adapter reads the real record and that his earlier backup was older). Record the outcome in the design file.

**Pitfalls**
- Test variables exported in your own terminal session persist into later commands and made the real run say the site was not in the list. Prefix variables on the one command (`SW_ENV_FILE=... python3 ...`) or `unset` them straight after the test.
- A float rounded in PHP can print with a very long decimal when the host's `serialize_precision` is -1; return a rounded string or integer minutes. Collect such cosmetic fixes and ship the plugin once, because each re-upload is Robi's work.
- A background notice that a test server has finished, after you already stopped it, needs one line, not a new report.
- `write_file` refuses to overwrite a script you have not fully read in this task. When the script is a live tool a running helper already calls, do not rewrite it in place: copy it to `<name>_v1_backup.py`, write the new version as `<name>_new.py`, test it, then `mv` it over the live name and run one real read as a regression check.

- Exposure probes recognise a leak by its shape (a log starts with a dated bracket, a .env has KEY= lines) and print only the path and meaning, never the content. Probe only listed sites, GET only, with a low fixed count of requests.
- Check any public data source LIVE before promising it. The reader's only file write is the cached list (6 hours) in the helper's own cache folder; the reader must name its source and licence link in every `vulns` answer.
- Run the reader's regression tests (unknown site, bad route, bad parameter, missing key, key file mode 644, key never printed) again after adding routes.
- Every `check_agent.py --scenarios` run repeats the live reads and the exposure probes of the helper's `tool` tests on the real site, including re-runs after an instruction fix. Say so each time you ask for the OK, not only the first time.
- Exposure probes look like a hacker's scanner (requests for `/.env`, `/.git/HEAD`, wp-config backups). Get Robi's OK before the first run on a live site and warn that a security plugin or the host's firewall may log it or briefly block his IP.

## 8. Helper rules for a deep scan with per-site notes
- Full-check order the helper follows and announces step by step: health, backup, uptime, exposure, plugins, wporg, vulns, themes, core, users, logins, errors, files (core and own code), then files per WordPress.org plugin one at a time; `code` only to list files or to read a file that `files` reported as changed. Every failed or empty step is reported as 'I do not have that data' with the reason.
- Report order: Urgent, Security, Updates, Health and speed, What changed since last time, What I could not check, then recommendation and what needs Robi's yes.
- Notes live in the helper's own folder (`Work/Sites/<site>/notes.md`, so test mode allows them), written only AFTER the report, after reading the previous note and comparing. Never put secrets, passwords, personal data (emails, IP addresses) or copies of code in a note.
- A helper whose output is per-client data must be placed in its own team folder at the first build (see `helper-with-companion-software.md`). The reader and its site list move with it: Robi copies the reader folder into the helper's `Assets/` (a copy, not a link, because the site list is client data too); the reader's default key file should try the new profile first and then the old one so both helpers work during the move.
- The site has one key, so the new profile needs the same line. Robi runs `grep '^SW_KEY_<SITE>=' ~/.hermes/profiles/<old>/.env >> ~/.hermes/profiles/<new>/.env && chmod 600 ~/.hermes/profiles/<new>/.env` (prints nothing). This deliberately bends 'never copy secrets between helpers' because the old helper is being retired: say so and offer a fresh key instead. Then check with `stat -f %Lp`, `grep -c` and the value's length (never print it), and do one live read.
- Note-writing rule that fixed a noisy file: one 'Current facts' block at the top that any check updates, and a dated entry added only after a FULL check. Otherwise every partial check (health, speed, backup) appends its own entry. Scenario runs write real notes to `Work/Sites/`, so tell Robi the test notes exist (you may not delete them).
- Add an 'answer first' rule: a helper with a note-writing duty answered a version question with only 'I saved a note'. A first wording ('answer first, note in one closing line') still missed in about 1 of 3 runs, because the model wrote its LAST message after the note and talked only about the note. What held (5 of 5 runs): 'your LAST message in every turn must itself contain the answer in its first lines; save the note BEFORE writing that message; a last message that only talks about a note is wrong'. Measure with the same prompt 5 times through `hermes -p <slug> --in <folder> -z`, then re-run `--scenarios`; a single PASS proves nothing.
- Cross-check numbers between the answers of one test report and against a live read: the plugin count came out as 15 in one answer and 16 in another because the plugin counts itself. Fix with a counting rule in the helper ('count as listed, say how you counted').

## 9. Second plugin version: history, change trail, malware-style scan, posture checks (still read-only)
Ship these together as ONE new version, with a zip, a test report and four upgrade steps (fresh backup; Plugins > Add New > Upload > 'Replace current with uploaded'; read the settings page back; copy the new reader). Key, mode and old data stay. Keep the old version's zip for rollback.
- **Ask before storing personal data.** Login history needs usernames and IP addresses. Put the retention (30 days), where it lives (the site only) and the choice (with IPs / without / counts only) to Robi as a `clarify` before coding; record his pick. Behind Cloudflare the server address is Cloudflare's: store the `CF-Connecting-IP` header separately and label it unverified. Never store or return passwords, including wrong ones.
- **Change trail from WordPress hooks** (`user_register`, `set_user_role`, `delete_user`, `activated_plugin`, `deactivated_plugin`, `deleted_plugin`, `switch_theme`, `upgrader_process_complete`), capped and pruned, with no IPs or emails. A saved baseline of privileged users, diffed on each users read, reports new admins, removed users and role changes; the first call only creates the baseline.
- **Malware-style scan = heuristics, say so in every answer.** Pattern ids only (file, line, pattern name, never the matching text): eval of encoded data or request data, command from request, known web-shell names, long encoded strings, remote include, auto-prepend directives; plus PHP inside uploads (except the empty 'Silence is golden' stub), double extensions, hidden PHP files, `.htaccess` redirects, and a list of PHP files changed in 7 days. Add a scope parameter (quick, uploads, plugins, themes, mu, root, all), a 25-second deadline that returns `partial: true`, a 1 MB per-file cap, no symlink following.
- **Make the scanner skip its own plugin folder**, or its rule list matches its own rules. The success test is a stock WordPress where the only findings are the planted files.
- **Plant test payloads without writing the literal string** in any test-only helper file (build it from base64 in the test mu-plugin), or the scanner correctly flags your own test harness and the 'clean scan' test fails.
- **Posture checks** (PHP support end dates, file editor, debug display, user named admin, open registration, XML-RPC, wp-config permissions, late scheduled tasks, disk space): take PHP end-of-support dates from php.net/supported-versions at build time and name the check date in the code; a version near its end is a warn, past it an eol. Robi's live site was on a version about six weeks from end of support, so this check earns its place.
- **Rate limit versus tests.** A 60-per-minute limiter answers 429 to a second test suite run in the same minute. Run suites one at a time on a fresh instance (baselines also block re-runs), wait a minute between them, and do not read 429 failures as plugin bugs.
- **Changing a response shape or type breaks older tests** (a renamed key, a number turned into text). Re-run the previous version's whole live suite on the new version on a fresh instance before calling it compatible, and update only the assertions that test the changed shape.
- Reader: add the new routes and parameter names to its allow-lists, copy it to the helper's `Assets/` again (Robi runs the `cp`), and re-run the reader's own regression tests.
- **Placeholder files cause false 'high' alarms on a real host.** Plugins leave tiny `index.php` files in upload folders. Report an `index.php` of 300 bytes or less with no request data, encoding, include or command words as LOW with its size, and keep anything else in uploads HIGH. Tell Robi plainly that the first live scan's highs are probably placeholders he can check once, and that you could not read the files.

## 10. Urgent-alert watcher (timer, no AI) and the 3-day digest
Needs Robi's separate OK for each timer and for the Discord target; ask the schedule first (time of day in Manila time, every 3 days, 24 hours a day or quiet hours) and have him confirm the list of 'wake me up' conditions. When he hands the judgment over ('think like a head of cybersecurity and uptime'), write the whole list in that voice (ping now vs digest only), then ask the one decision that is his (for example: pings at any hour).
- **Mechanism (Hermes docs, `hermes-reference` section on timers):** the digest is an agent job (AI runs the full check, result delivered to the channel). The urgent watcher is a script-only job: the script prints NOTHING when quiet and an alert only when something new and serious happens; empty output posts nothing, a non-zero exit posts an error alert. The script lives in the helper's scripts folder, which Robi must copy into (agent-creator cannot write outside `briefs/`).
- **Watcher script rules** (`briefs/<reader>/sw_watch.py`, imports the reader's functions; run every 30 minutes): checks cheap things only (home page status and speed, SSL days left, plugin health, backup age, users diff, change trail, login counts, quick scan, and every 6 hours core files and the vulnerability list). Conditions it raises: site down or very slow (look twice 20 seconds apart before alerting), SSL invalid or under 14 days, the plugin not answering while the site is up (critical: an attacker may have switched it off), backup failed or over 48 hours old, new or changed users, new high scan findings, a burst of failed logins (alert at 20, 40, 60 a day), a login from a new address, plugin switched off or deleted, theme switched, core files differ, a new non-informational vulnerability.
- **First run sets baselines and says so once** ('watching started', how many existing high findings were accepted), and alerts about nothing that already existed except real states (a stale backup, a known hole). Point-in-time feeds (change trail, logins) keep a 'seen up to' pointer so each event alerts once.
- **Dedupe key = condition id + title + only the stable facts.** Numbers that drift (seconds, days left, ages, running counts) must not be part of the key or every run re-alerts. Re-send a still-open serious problem once every 24 hours as 'STILL OPEN', and send 'Back to normal' when it clears. If the site is down, skip the plugin checks so one outage is one alert.
- **Silence discipline:** capture the stdout of helper functions that print `STOP:` so only real alerts reach the channel; a second run while one is running exits quietly (file lock); the memory file is one small file in the helper's cache folder, mode 600, with no keys; a crashing check becomes one 'the watcher hit a problem' alert, not a stack trace every 30 minutes.
- **PHP prints an empty list as `[]`, not `{}`.** Every Python reader of the plugin's JSON must treat a field that should be a dictionary but is not one as empty (a small `dct(x)` helper before every `.get`). A watcher that skipped this crashed on a site whose login history was still empty, which is exactly a freshly upgraded live site. The crash showed up only as the watcher's own 'hit a problem' alert, so keep that alert and add a test: first run on an empty history must not report it.
- **Plugin-driven test steps.** Give the throwaway site a test-only mu-plugin endpoint (`?sw_act=<name>`) that causes the change under test (add an administrator, change a role, activate a plugin, plant a file built from base64, set a fresh backup record, switch the watchdog plugin off and on), and post real wrong and right logins to `wp-login.php`. Stop and restart the server for the site-down and recovery steps (`start.sh` and `stop.sh` helper scripts, about 60 seconds to be ready).
- **Wiring the timers (Robi's OK first; dry run on the live site first is fine, it is read-only and prints what the first message would be):** `hermes -p <slug> cron create "every 30m" --no-agent --script <wrapper>.sh --deliver discord:<channel id> --catch-up on --name <site>-watch` and `hermes -p <slug> cron create "0 9 */3 * *" "<self-contained digest prompt>" --timezone Asia/Manila --deliver discord:<channel id> --catch-up on --workdir <helper folder> --name <site>-digest`. The script must sit under the profile's own scripts folder and resolve inside it, so a two-line `.sh` wrapper there `exec`s `/usr/bin/python3` on the watcher in the helper's `Assets/site-reader/` (no copy of the key, sites or reader into the scripts folder). Copy the new `sw_watch.py` and `sw_read.py` into `Assets/site-reader/` and write the wrapper (`chmod +x`) either by giving Robi the three lines or, when he is away from his Mac and asks you to do it, yourself after his explicit ask: these are non-secret files in the helper's own folders, and say plainly that you stepped outside `Agents/` because he asked. Run the wrapper once with `SW_WATCH_STATE=<temp file>` set to prove it prints the start-up message without touching the live memory file, and check `cron list` and `cron doctor`. `*/3` in the day-of-month field restarts at each month, so the gap is one day at month end: tell him. Verify with `hermes -p <slug> cron list` and one manual run.
- **The plugin's flood limiter is global** (it also counts unsigned requests), so an attacker hammering the routes makes the watcher see 429 and raise 'plugin not answering'. That is acceptable, but say so. The watcher uses about 9 requests per run, far under 60 a minute; in tests pause about 12 seconds between watcher runs or later steps fail with 429 and look like watcher bugs.
- **Tests that proved it (on a throwaway site, each step also run twice to prove it stays silent the second time):** first run message; quiet run prints nothing and changes no site data; new admin plus role change; planted web shell names the file but never its code; failed-login burst; login from a new address; backup fixed gives 'Back to normal'; plugin switched off gives the critical alert and switching it on recovers; wrong key reads as 'not answering'; the memory file holds no key and is mode 600; a 24-hour-old open alert repeats as STILL OPEN; `--dry` saves nothing; the site stopped gives DOWN, still down is silent, restarted gives 'Back to normal'.
- **Blind spot to tell Robi:** if the Mac is off or asleep nothing is watching. Offer an external heartbeat (a free uptime monitor that alerts when the Mac stops checking in) as a later step with its own yes.
- Never create the timer yourself without his clear OK; when he gives it, create the digest and the watcher for the helper's own profile, deliver to the site's channel by id, and verify with `hermes cron list` and one manual run before calling it live.

## 11. Write side: approved changes (clear cache, block an address, update one plugin)
Stage after the read-only plugin, watcher and digest work. Each stage needs its own plan and yes. When Robi says 'all' of the actions, build them safest first (cache, block, update) in one plugin version, but say plainly that a helper's 'ask first' rule is only a rule, so the limits must be enforced by the plugin and not by the helper. Ask for his OK to those limits before coding.
- **Plugin-enforced limits:** only the named actions exist (anything else is refused, extra fields ignored); no delete, no code edit, no core or theme update, never the watchdog's own plugin, no single-file plugins, major version jumps only with an explicit flag, a switch on the settings page (off by default), a fresh backup (under 24 hours) and a passing site self-test checked at proposal time AND again when the code arrives, a daily cap (3), a cap on proposals waiting (5), 24-hour expiry, every proposal and result in a capped record and posted to Discord.
- **The helper must not be able to approve itself.** The helper only PROPOSES through a signed POST. The plugin posts the one-time code straight to the Discord channel through a webhook constant in `wp-config.php` (Robi creates the webhook and pastes it there; the address is a secret, never in chat, files or logs), and the proposal answer carries no code. Robi types `yes <id> <code>`; only then does the helper call confirm. Three wrong codes lock the proposal; a used, declined, expired or locked proposal cannot be approved. If the webhook post fails, the proposal is not created. Tell Robi the helper does see the code once he types it, and that a hidden instruction planted in site data could still try to trick the helper, which the limits reduce but do not remove.
- **Signed POST:** include the SHA-256 of the body in the signed text (a GET signature or a signature that ignores the body must fail), same timestamp window and replay guard as the reads, POST-only routes, generic 401 for every refusal.
- **Blocking an address:** accept only public addresses (reject private, loopback, reserved, garbage); never Cloudflare's published ranges (refresh weekly, ship a default list); never an address that logged in successfully lately or called the plugin; auto-lift after 7 days; a cap on the list; a settings-page button to unblock all. Believe `CF-Connecting-IP` ONLY when the connecting address is inside Cloudflare's ranges, otherwise a fake header lets an attacker dodge a block or get an innocent visitor blocked. Test with a test-only mu-plugin that sets `REMOTE_ADDR` from a query parameter before the plugin loads.
- **Updating a plugin:** first re-check that WordPress still offers exactly that version (its update list can be refreshed between proposal and code; if not, change nothing and say so). Keep the old version as a ZIP (PclZip from `wp-admin/includes/class-pclzip.php`, works without the zip extension) in the plugin's own protected folder under `wp-content/` (not under `wp-content/upgrade`, which WordPress empties before it unpacks ANY update, so a copy kept there is gone when you need it), with an unguessable file name, an `index.php`, an `.htaccess` deny, pruned after about 3 hours and removed on uninstall; check the zip exists and is not empty BEFORE touching the plugin. Then upgrade with `Plugin_Upgrader` and `Automatic_Upgrader_Skin`, check the new version reads back as the proposed one, switch the plugin back on if it was active, THEN run the site self-test. A plugin that will not switch back on counts as a failure, not a pass. On any failure restore from the zip (`unzip_file` after deleting the folder) and report whether it worked; make the restore function return the plain reason when it fails (and include the upgrader's own messages in a failed update) so the Discord message says why; if the restore failed, say to use the backup. Refuse when the filesystem method is not `direct`.
- **Self-test after every change:** load the home page and login page, fail on 4xx/5xx or fatal-error text, report what passed. Put a filter hook in it so tests can force a pass, a fail, or a fail only after the change (counter per request), which is how rollback paths are proven.

## 12. Plug-and-play sites: pairing, encrypted key, add-site command, per-site timers
When Robi says adding a site must be 'plug and play' and 'tested here', plan it as one stage (plugin version + Mac command + small helper update). He may choose the easier option over the safer one (key in the plugin's settings instead of wp-config): state the trade-off in one plain paragraph, recommend the safer one, then build his choice with the protections below and say what the remaining cost is.

**Plugin (pairing and secrets)**
- Store the key and the Discord webhook encrypted in the database (AES-256-GCM via OpenSSL, nonce per secret, the purpose `k`/`w` as authenticated data so one blob cannot pass for the other, a derived key from HKDF over ALL eight wp-config keys and salts). A database copy or an UpdraftPlus backup then shows nothing. Refuse to store anything when a salt is missing, short, repetitive, duplicated or still the sample text (check the sample text BEFORE the length so the message names the real cause) and tell the admin how to fix it; rotating the salts later makes the stored key unreadable, so the settings page must say 'reset and pair again', not crash. Keep the pure crypto in a WordPress-free class so it is unit-tested alone (tamper, wrong salts, wrong purpose, truncated, garbage, empty secret refused).
- Pairing: an admin button (capability and nonce) creates a 10-character code (about 50 bits), stored only as a salted hash, valid 15 minutes, 3 tries, one use; show it once by putting it in a short per-user transient that the next page load displays and deletes. The pair route is the only unsigned route: HTTPS only, rate limit first, the same generic refusal for 'no pairing started' and 'wrong code' (nothing to learn), a wrong code that is not the third leaves the pairing alive, the third cancels it and warns Discord, a bad webhook in the request does not burn the code, the answer is `Cache-Control: no-store` and shows the key once. Choose Simple or Careful at pairing time (default Careful).
- A leaked key must not redirect approval codes: the webhook can be set only by a logged-in admin (settings form with a password-type field that never shows the value, or remove it) or inside a valid pairing request, never through a signed route. Changing it posts a warning to the OLD destination. 'Reset connection' deletes only the key, cancels waiting proposals and posts a warning. The old wp-config constant keeps priority so existing sites work unchanged; the settings page says which way it is connected.
- Sites backed up another way (cPanel): an admin button 'I made a backup just now' counts for 24 hours, is labelled admin-confirmed and unverified in the backup read and in every proposal message, and loses to a fresh UpdraftPlus record. Without either, monitoring still works and changes are refused with a plain reason.

**Mac command** (`sw_add_site.py add | doctor | list | remove | migrate`, run by Robi, not by the helper; the helper's rules allow only the reader and the change tool)
- Order: plain-words preflight (DNS, certificate days, home page, firewall or challenge page, redirect, REST index lists the plugin's namespace; each failure says what to do and nothing is created) then hidden pairing-code entry (getpass, or stdin when piped) then Discord channel and webhook (reuse an existing channel only when its topic starts with the tool's marker) then pair with the webhook in the same call (undo only the Discord objects made in THIS run if pairing fails) then save the key to the private file FIRST (atomic write, mode 600, refuse the write if any existing variable would disappear), verify with a signed read, add the channel to `DISCORD_FREE_RESPONSE_CHANNELS`, create the two timers, start the notes file, run the watcher once for baselines, post a summary into the channel, restart the gateway (Discord channel settings are read at gateway start, so each new channel needs one restart; ask him or take `--yes`).
- Make it resumable: the site entry carries `setup_done` steps and `setup_complete`; running `add` again for a half-finished site finishes the rest and never pairs twice. Exit 3 for 'not finished', 2 for a refusal.
- Print nothing secret, ever; test by searching every run's output for the key, bot token, webhook token and pairing code.
- Hermes pieces used: `hermes -p <slug> cron list --all`, `cron create ...`, `cron remove <job id>` (parse the id from the list output), `-p default gateway restart` as a delayed background process. Discord API needs the bot's Manage Channels and Manage Webhooks (a 403 gets a plain message naming both); build the webhook address from the returned id and token.
- **Per-site watcher**: add `--site NAME`, one memory file and one lock per site (a shared file loses updates, and a shared non-blocking lock silently skips a site), import the old shared file's entry the first time, stagger the digests' minutes, and make a watcher started WITHOUT `--site` while two or more sites exist print a loud STOP and exit 2.
