# Agent lifecycle (end to end)

### ALWAYS leave a working, explorable architecture & user map when auditing the Hermes environment
- For a full audit of the Hermes Mac environment (helpers, status, profiles, skills, tools, memory, providers, tool connections…) write one interactive visual HTML guide as a new file. Do **not** change, delete, or disconnect anything.
- Discover the system live (never rely on session history). Run broad shell/tool queries, read config and status, and check for real evidence (passing checks, session history, process state) to separate working features from planned or old.
- Show real examples. Note where helpers, tests, or projects only exist on paper vs where real use/test/session evidence is found. Clearly map “working”, “built & tested”, “experimental”, “planned”, “old” and “needs attention”.
- Present for a non-technical owner: short, plain language, real diagrams, clickable architecture map, helper index, user scenarios, and a practical “which door/tool for which job” wizard. Mark all gaps or risks (model mismatches, old files, missing promotion or test status, inactive connections, etc). List them at the end in priority order.
- Link to the live working HTML file; update the “how to use” step to mention always delivering an explorable interactive guide after an audit.
- Use the current rules above for always-on approvals, separation of preview/testing/stale vs live, and one job per helper.
- “Nothing to save” is not the default after an audit: for a full environment review, capture the plain-language expectation that EVERY future audit leaves an actionable “map and guide” visible to the owner as output. This avoids invisible or inactionable audits.

The ideal outcome: Robi says "I need a helper for X" and ends with a helper that is **understood, built correctly, connected to the tools it needs, tested, documented, used correctly, and reviewed**. You own that whole outcome. A helper that was only "created" is not finished.

Always tell Robi where you are in one short line: **"Step 3 of 10: writing the plan."** Never skip a stage. Never say "done" for a stage until its exit check is true.

Rules for how things are organized are in `~/Team-Workspace/Agents/CONVENTIONS.md`. Hermes facts are in the `hermes-reference` skill.

## The 10 stages

| # | Stage | You do | Exit check (all true) |
|---|---|---|---|
| 1 | **Discover** | Interview (socratic-discovery), map workflow, user journey and customer journey | Readiness gate in `agent-requirements` is true and Robi said "yes, that's right" to the teach-back |
| 2 | **Shape** | Decide fit (no helper / existing / new), one job, placement, name, tools, memory, model, limits, how it is reached | every row of the requirements table has an answer or a named Unknown |
| 3 | **Brief and approval** | Write the Agent Brief with tests; show the plain-words part | Robi said a clear yes to "Shall I build it as written?" and Status is APPROVED |
| 4 | **Pre-build check** | `hermes status`; gateway running; model works; name free; placement valid; secrets plan; dry run | dry run prints the plan with no STOP |
| 5 | **Build** | `create_agent.py --approved --smoke` | script says BUILT; smoke answer is sensible and exit 0 |
| 6 | **Connect tools and reach** | Only what the brief lists: outside tools, and a Telegram bot if it will be reached there (below) | each connection passes `mcp test` and one harmless read; Telegram shows connected and has answered a hello |
| 7 | **Verify** | `check_agent.py <slug> --scenarios`; explain results plainly; fix and re-run | no FAIL; every REVIEW read with Robi |
| 8 | **Hand over** | Give the "How to use your helper" card | Robi can say how to ask it, what it asks first, where its work lands |
| 9 | **First real use** | Sit through one real task with Robi | Robi says the result was right (then `registry.py set-status <slug> production --approved`) |
| 10 | **Review** | After three real tasks or seven days, then monthly | review recorded; decision: keep, change or retire |

## Stage notes

**Removing a project's helpers.** A request to delete a project's rows, files or generics is not a lifecycle stage and no script does it: read `references/repository-and-new-project-setup.md` section 4 first (survey, briefs files, registry rows through a one-off script that uses `registry.py` load/save, generics one at a time).

**2 Shape.** For organizing the helper library (generic vs project-specific) or for a client, project or department that has no folder yet, read `references/repository-and-new-project-setup.md` first. Ask about: *where it lives* (a client's folder, or its own team folder), *what tools it needs* (plain questions: browse the web? read and write files? run commands on the computer? create images? work on a timer? talk to other helpers? use an outside tool such as Jira, Notion, Drive?), *how Robi will reach it* (Hermes app, terminal, Telegram, another helper), *how strict the fence must be* (on this Mac a folder limit is a rule it follows, not a wall; say so plainly). Choose the lean setup: only the toolsets and skills the job needs (`toolsets_off`, `skills_mode: lean`). Ask where its notes and outputs will live: anything per-client (site notes, records) must not sit in `Agents/` (definitions only), and placement cannot be changed later, so pick the team folder before the first build.

**Visual plan before approval.** When Robi asks for "the plan visually" or a "bird's-eye view" while discovery is still open, this is not a build and not the brief: write a self-contained HTML file to `briefs/<name>-plan-visual.html` (or `-birds-eye.html`), show it inline with `::preview{file="..."}`, label it DRAFT, and keep a visible "Still unknown" list. Use the app's theme variables and no custom background. First give the parts and the main flow; if he wants the whole picture, add one page with lanes (his existing system, the helpers, knowledge sources, admin side), a table of the uses side by side, the repeating cycle, a phased roadmap with who does each phase, and the decisions still needed. Say in the reply that nothing is built, name the biggest gap, and still end with exactly one question. Probe the real environment before offering options for the gap. Scanned source books: this Mac has `pdftotext` and `pdftoppm` but no `tesseract` or `ocrmypdf`, so scans cannot become text without a new tool. Offer the real choice (install with his OK, or read page by page, which is slow) and record his pick; the books are his own copies and must not be stored inside `Agents/`.

**3 Brief.** Put real tests in the build spec `tests:` (see below). Show only "In plain words" and the limits to Robi, not the technical block.

**4 Pre-build.** Run `hermes -p agent-creator status`, `python3 ~/Team-Workspace/Agents/bin/registry.py status`, then the dry run. If the gateway is not running or the name is taken, stop and say so.

**5 Build.** Run the dry run, then the real build. Report in plain words: where it lives, what it is called, what it can and cannot do, and that it starts as **testing**.

**6 Connect tools and reach.** If the brief's `reach` includes Telegram (needs Robi's OK): this agent needs its own bot. Tell Robi, in plain words: (1) easiest, open the Hermes app, Messaging, Telegram, choose this helper and use "Create with QR", which does everything and restarts the gateway; or (2) make a bot with @BotFather and run `hermes -p <slug> gateway setup`. He, not you, handles the token and gives the numeric user ID to the setup. Before any gateway restart check that no task is running. Then run `check_agent.py <slug>`: it must show Telegram connected; then Robi confirms with `/whoami` in the chat that only his own account has access. If Robi sends voice notes (ask in the interview), make sure speech to text works first (`hermes-reference`, Voice notes). Finally ask Robi to send the bot "hello" and a short voice note from his phone and confirm it answers in short, plain messages. Use the `hermes-reference` failure list if not. If the helper must send a file for approval (an invoice PDF), lives in a group chat, or a second person is to use it, read `references/telegram-groups-and-file-delivery.md` first.

**Discord:** the build script's `reach` list has no Discord, so a Discord helper is built with `reach: app` and Discord is connected here by hand (`hermes-reference`, Discord): Robi creates the bot and keeps the key, an allowlist of the named people's numeric IDs, then a real hello. Say plainly that `check_agent.py` does not verify it. For the restart procedure and the setup traps (allowlist prompt, free-response channel, stale settings until restart) read `references/gateway-restart-and-discord.md` first.

**Outside tools** (needs Robi's separate OK for each connection):
1. Choose the method: a built-in toolset, an MCP server, a skill with its own key, or a hosted connector (`manage_connections`: Robi signs in in the browser, no key in chat). A hosted connector connects the tool to YOU, the builder, so use it during the interview to read the real setup (folders, lists, custom fields, task statuses). The new helper still needs its own connection after approval. Read only until Robi says otherwise; the connector cannot be limited to read-only on your side, so say so plainly. Uploaded policy documents may be outdated drafts: compare them with the real tool and show Robi any differences instead of choosing. When Robi's own answer departs from the document, say so in one line and record it as his decision, not the policy's. For saving files into Google Drive no hosted connector exists, so use the options and warnings in `agent-requirements` `references/document-in-document-out-helper.md` (section 3, output name pattern and where it is saved). Before calling something unreadable, search for a tool that shows it (`tool_search` "get list" returns a ClickUp list's statuses). Check every name Robi gives (statuses, fields, lists) against the real tool, and show him a mismatch. If the tool truly cannot show it, treat it as an Unknown, ask Robi, and re-check it in the helper's tests.
2. Secrets: Robi stores the key himself in that helper's `.env` (permissions 600) or the Mac Keychain. You never see it, never type it, never put it in a file. Tell him the exact place, in plain words, and walk him through it one small step per message (create the key, copy it, run the hidden-paste command, tell you 'saved'). The exact command and the checks that confirm the value without printing it are in `hermes-reference` section 6 ('Placing a key without seeing it'). Do not connect the tool until a read-only call with that key returns success.
3. Add the connection to that helper's `config.yaml` (`mcp_servers`, include only the tools the job needs, read-only first, secrets as `${VAR}`), or let Robi run `hermes -p <slug> mcp add`. For a catalog OAuth server (`hermes -p <slug> mcp install <name>`) the entry starts with every tool enabled: tell Robi not to use the helper until he has signed in (`mcp login`) and you have cut the tools to read-only (`hermes-reference` section 6). Never report the connection as read-only until `mcp list` shows a filter.
4. Verify: `hermes -p <slug> mcp list`, `hermes -p <slug> mcp test <server>`, then ask the helper for one harmless read and check it. If it fails, use the failure table in `hermes-reference`.
5. Record the connection in the brief and write a CHANGELOG line.

**6 with nothing to connect.** If the brief has no outside tools and `reach` is `app` only, there is nothing to connect: say so in one line and go to stage 7.

**7 Verify.** Run `check_agent.py <slug> --scenarios`. When a toolset is on only for a narrow use (for example `web` to open given links), also query the helper's `state.db` for calls it must never make (`tool_calls like '%web_search%'`) and report the count. Explain the result without jargon: what passed, what needs fixing, what Robi must read. Fixes to instructions go through an updated, re-approved brief and `create_agent.py --update` (it backs up first). Re-run until there is no FAIL. The report is saved as `briefs/<slug>-test-report.md`.

The summary prints only `[REVIEW] scenario:<kind>`, so two tests of the same kind (two `edge` tests) are ambiguous. Open the report and search for `: REVIEW` to find which prompt it was, and give each test a distinct prompt.

The saved report cuts each answer short (about 600 characters), so a closing part such as an options menu or a rubric tick can be invisible. Re-run the one test that matters most with `hermes -p <slug> --in <folder> -z "<prompt>"` and read the full answer before saying it works.

When a helper says it cannot access an attached PDF or document, do not assume the file tool is broken. Check its `state.db` for the attachment message and saved path, then run a one-shot reproduction with that exact path. If the reproduction reads the file, update the brief so the helper must try attached file paths before asking Robi to retype, and add a document-attachment scenario using a real harmless file.

Run scripts with `/usr/bin/python3` when started in the background (plain `python3` there can be a Python without `yaml`, and the script dies before any test runs). One-shot test runs (`-z`) allow only 2 sub-helpers in total (`delegation.oneshot_max_children`), so a delegation test asks for 2, and real use is confirmed in the helper's `state.db` (`tool_calls like '%delegate_task%'`, plus child sessions). A PASS is not proof. The scenario check passes when the answer contains one of the `expect:` words, so a `tool` test can pass without the connection being real, and the report can contradict itself (one answer says it has no ClickUp tool, another quotes ClickUp data). Read the answers, verify the claims yourself against the live tool, and look in the helper's history for how it got them. If it reached a tool you never connected, a toolset is on that should be off (`hermes-reference` section 5, the `connections` side door). Report the gap, propose the fix as an updated brief, and say the helper is not yet working.

Write tests in the brief like this (kind | prompt | expect: words it should use):
- `intro` — it states its job and its folder.
- `normal` — the first test task from the user journey, in test mode.
- `edge` — an unusual but realistic request from the workflow's exceptions.
- `boundary` — a request that must make it ask first or refuse (sending to a client, deleting, spending).
- `scope` — a request to look at another client's files (client agents).
- `tool` — one harmless read through each connected tool.
Pick `expect:` words that only a correct answer contains, not words that also appear in the prompt or in a report layout label. For boundary tests about missing data, make the helper's instruction require a short exact phrase (for example "I do not have that data") and put that phrase in `expect:`; otherwise the answer may ask for the data correctly while the word check still fails. For a calculation test, give small sample data, work out the right answer yourself first (for example the right aging bucket, "31 to 60" for a 41-day-old invoice), expect that figure, and check the arithmetic the helper shows when you read the answer.
Test runs are always "test mode": nothing is sent, published, deleted, spent or changed outside its Work folder.

**8 Hand-over card** (plain words, give it to Robi and save it ONLY as `Agents/briefs/<slug>-how-to-use.md`. Never write into the helper's own folder (no `Work/how-to-use.md`, no edits there), even to correct the card after a rename or an update: agent-creator may write only inside `Agents/briefs/`. Offer a copy in the helper's folder only if Robi asks and the house rules allow):
- **What it is for** (one sentence) and **what it will never do**.
- **Where to find it**: the Hermes app under Bots, or `hermes -p <slug> --in <folder> -z "<request>"`.
- **How to ask**: three example requests taken from the user journey.
- **What it will ask you first** before acting.
- **Where its work lands**: drafts in `Work/`, approved files in `Deliverables/`.
- **How to correct it**: say what was wrong; it saves lasting lessons to its memory. Bigger changes go through `agent-creator`.
- **How to check on it**: the test report, and `hermes sessions list` for what it has done.
- **If it stops answering** (only when its model login can expire, as on a subscription login): the exact renewal command Robi runs himself, and the rule that any code goes into the terminal, never into chat.
- **When we review it**: the date.

**9 First real use.** Ask Robi for one real task (if he attaches a document, that is the task: read it with `read_file`, which extracts .pptx/.docx/.pdf text, so you know what the helper should produce, and say which choices you carry over from the source, such as the project name and slide order). Run it with `hermes -p <slug> --in <folder> -z "Real task, not a test. ... <attachment path> ..."` in `terminal(background=true, notify=true)` writing to `$TMPDIR`, since a real build runs past the foreground limit. Read the output with `cat $TMPDIR/<file>` in the terminal: in a background shell `$TMPDIR` is a system folder, not the scratch path named in the prompt, so a guessed `read_file` path is not found. For a team builder (multi-agent-engineer) read `references/team-build-first-task.md`. Then verify the output yourself (run the helper's checker on it, read the content against the source) before telling Robi. Scenario tests leave test outputs in the helper's `Work/`; tell Robi, you may not delete them. Stay with it. Afterwards ask: "Was that the result you wanted? What surprised you?" Only a clear yes allows promotion. If he says he cannot judge the result (a practice task with no real project), that is not a yes: show him the output itself and keep the helper in `testing`. A "mostly" means go back to stage 7 or 5 with a change. When he asks "is it completed?", answer with two short lists, done (built, check result with numbers, real tasks run) and not done (promotion yes, known gaps, hand-over card refresh, review date), then ask whether to keep testing or promote. If Robi says "later", leave the helper in `testing`, say in one line what is waiting (first real task, promotion, review date), and follow his next request; do not push.

**10 Review.** Ask: What worked? What annoyed you? What did it get wrong? What should it never do that it did? What is it missing? With Robi's permission look at `hermes sessions list` and `hermes logs errors --since 7d` for this helper. Change what is needed through an updated brief. Record it with `registry.py review <slug>`. Decide: keep as is, change, or retire (`create_agent.py --retire <slug> --approved`, which keeps the brief and registry row).

## Pitfalls learned

- `check_agent.py` passes a `boundary` test only if the answer contains an ask word (ask, approval, cannot, won't, before ...). A correct refusal such as "That is for a project manager helper. I don't run teams" FAILS it. For a "wrong job, belongs to another helper" refusal, write the test as `edge | ... | expect: <the fixed phrase>` instead, read the answer first, and tell Robi plainly that the test wording (not the helper) was wrong. Reserve `boundary` for "must ask first" cases.

- The bin scripts hard-code Mac assumptions: every path comes from `$HOME`, and `create_agent.py` always wires the Anthropic key route. Before building on any other machine, read `hermes-reference` `references/vps-docker-copy.md` and check the machine's real model route in the pre-build stage; a profile built with the wrong route exists but cannot answer, and every later `--update` resets the route again, so re-set it and re-run the hello test after each update.
- A fixed-phrase `edge` test (for example 'That is a later stage.') can flip between PASS and REVIEW across runs because the helper paraphrases ('X is a later stage'). Write such an `expect:` as the short fragment without capital or final full stop ('later stage') so a merged sentence still matches, and keep the exact phrase in the helper's instructions. Read the answer; if the meaning and the refusal are right, report it as a wording slip in a word-match test and change nothing. To find the REVIEW entry use `grep -n ": REVIEW" briefs/<slug>-test-report.md` and `read_file` at that line (an `awk` range on the heading prints nothing useful). For a new rule's test, also re-ask the prompt 3 times by hand with `hermes -p <slug> --in <folder> -z` before saying it holds.
- A test report's `[REVIEW]` on a `tool` test often means the helper answered a side duty (saving a note) instead of the question. Open the report entry, compare it with the prompt, and fix by an 'answer first' rule through an updated brief; do not reword the test to pass. Re-ask the same prompt 3 to 5 times before and after: if some runs still skip the answer, tighten the rule to 'the LAST message must itself contain the answer; do side duties (notes) before it' and measure again (details in `agent-requirements` `references/wordpress-plugin-build-and-test.md` section 8).
- Never `export` test-only variables in the terminal session: they stay set for every later command and can silently redirect a live run (it said the real site was unknown). Put them in front of the one command, or `unset` them straight after the test.
- When Robi's stated fact ("the backup is from today") and a real tool read disagree, do not choose a side and do not argue. Say both, then run the small test that tells them apart (he makes a new backup, you read again) and record which was right.
- Run `check_agent.py` and the other bin scripts with `/usr/bin/python3`, not bare `python3`. A backgrounded shell can pick a Python with no `yaml` module and crash with ModuleNotFoundError; the helper is fine, only the command was wrong. A crashed background run leaves the OLD test report on disk, so read the output file (`EXIT` line, summary) before reading the report. Run `--scenarios` for a helper with delegation on in the background from the start (`terminal(background=true, notify=true)`, output to the scratch folder): the foreground tool times out at about 420 seconds and the team tests alone exceed it.
- Helpers with delegation on (recipe: `agent-requirements` `references/helpers-with-workers.md`): scenario tests only prove the helper can describe a split, and a word-match PASS can hide that no worker ran. Run one real, clearly fictional task (`hermes -p <slug> --in <folder> -z ...`) that asks for at most 2 workers and read the full answer for a real "Workers used" line. One-shot runs allow only 2 workers in total (`delegation.oneshot_max_children`); a bigger request is refused, the helper does the job alone and says so. App and gateway sessions are not limited, so confirm a full worker team on the first real job in the app.

- After every `create_agent.py --update`, check that the registry row matches the brief (`toolsets_off`, tests line). If the row is stale, `check_agent.py` FAILs on a setting that is actually right in the helper's config; re-run the same approved `--update --approved` rather than editing `registry.yaml` (details in `agent-requirements` `references/helpers-with-workers.md`, section 4).
- A profile name cannot have spaces or capitals ("Chief Marketing Officer" becomes `chief-marketing-officer`), and no script renames a helper. To rename: tell Robi the exact slug first, write a new brief with the new name (copy the old brief, change `name:` and the name rows, keep the old brief as history), build it, run the full checks, then `create_agent.py --retire <old> --approved` and `registry.py sync`. Get Robi's yes to both steps first. The home folder can stay the same; update the hand-over card copy in `briefs/` with the new name.
- `write_file` refuses to overwrite any existing file in `briefs/` (a brief, a hand-over card) that this task has not read in full, or read only with `offset`/`limit` pages. Read every page first, or edit with `patch`; for a long brief prefer `patch` so unrelated lines survive. Do this before refreshing a hand-over card after an update.
- Every approved update that changes what the helper does leaves its hand-over card (`briefs/<slug>-how-to-use.md`) describing the old version. After the re-check passes, refresh the card in `briefs/` (new rules, new tests, new limits) and say so, or list it as not done.
- Keep any change to a built helper as a separate draft file (`<name>-vN-draft.md`) until Robi says yes, so `--update` cannot apply an unapproved brief. Validate the draft with `create_agent.py <draft> --dry-run --update`. After his yes: copy the live brief to `<name>-vN-archive.md`, `mv` the draft over the live brief (so no stray draft is left), set the Status line to `APPROVED ... Update vN approved by Robi on <date>: <what changed>`, then run `--update --approved --smoke` and re-run `check_agent.py --scenarios`.
- Before telling Robi what an update changes, count the tests in the draft (`grep -c '^  - \(intro\|normal\|edge\|boundary\|scope\|tool\) |'`) and diff the draft against the live brief; never state the new test total from memory. If the count differs, fix the requirements table's `Tests` row in the draft too, and correct any number already given to Robi in plain words.
- `patch` is fuzzy: inserting a block directly before a line like `tests:` can swallow the line break and merge `tests:` with the next test line. After any patch near a build-spec key, re-read that region and re-run the dry run with `--update`; the test count must match. A `connections:` list in the build spec only records the connection in the registry. The real `mcp_servers` entry is added at stage 6 with his separate OK, so say that when asking him to apply an update that lists one.
- When Robi overrides a risk recommendation (a platform's scraping terms, 'it is legal if I use the tool'), give the facts once with a source and the clause, say plainly you are not a lawyer, record it in the brief as HIS decision with the risk named, and build the narrowest fences he accepts (scope, caps, add-ons off, his yes per run). Do not re-argue and do not quietly refuse; do not loosen unrelated rules to match.
- Loosening an approved rule (for example allowing one add-on that was refused) leaves the old fixed phrase in several places. `grep` the draft for it and change the instructions, examples, plain-words text, requirements table and every test that expected it, then re-count tests and re-run the dry run.
- Do not put backslash-escaped quotes (`\"`) inside a build-spec `instructions:` line: they reach the helper's SOUL.md as literal backslashes. Use single quotes for any phrase the helper must say.
- A helper that calls agent-creator in the background (for example a team builder asking for a missing generic helper) gets a one-shot run where you cannot ask Robi. Save the request as a draft brief in `briefs/` with Status DRAFT, never build, never set APPROVED, and reply that Robi must open agent-creator to approve it.
- A helper that saves notes or files can PASS its `normal` test in test mode without saving anything (test mode forbids writing outside `Work/`, so it only describes the steps). Before calling it working, run one real save and a read-back with a clearly fictional fact, and check the file on disk. A generic note keeper must also answer an unknown question with its fixed phrase, not a guess.
- A `boundary` test for a correct refusal that holds no ask word (for example 'I do not store passwords') FAILS the check: change it to `edge` with the fixed phrase in `expect:` via an approved update, and tell Robi the test wording, not the helper, was wrong.
- Drafts that a team builder requested (`<role>-draft.md`, Status DRAFT) are approved in Robi's own chat: show the plain-words part, list your assumptions, and say plainly that no script marks a helper generic or places it in the repository, so the drafts are built straight into `team:<Folder>` as the members. On his yes: set Status to APPROVED with the date, save as `<name>.md` (the build-spec `name:`), `--dry-run`, `--approved --smoke`, then `check_agent.py --scenarios` in the background. The first `-draft.md` copies remain in `briefs/`; mention them, do not delete. For several drafts at once: `sed` line 3 into each `<name>.md`, dry-run all, build all, then run the three `--scenarios` checks in ONE background loop (`for n in ...; do /usr/bin/python3 bin/check_agent.py $n --scenarios > $TMPDIR/check-$n.txt 2>&1; done`) because the foreground tool rejects a shell `&`; read each output file, not just the saved reports. Then add each role to `briefs/GENERIC-HELPERS.md` (table row plus the Updated line) when Robi asked for generic roles. A helper built later from a new interview is not covered by an earlier request: finish the build and checks, then ask once whether to index it before editing the file.
- After editing an index or list file (for example GENERIC-HELPERS.md), grep for the new row before saying it is added: `patch` with identical old and new text reports `no_change` and writes nothing, so use a replacement that differs from the anchor and re-check.
- A bare 'ok' or 'go' to a message that held two questions (promote this one, apply that update) covers only what he was clearly asked: do the part that needs no new approval, and for an update to a built helper show the plain-words change and ask 'Shall I apply it?' again. Draft the update in a `-vN-draft.md` file, never in the live brief.
- A first real task for a team member that handles files is a clearly fictional one passed with `-z` (made-up company, made-up source text, today's date stated). Afterwards `read_file` the file it wrote, report what it did and did not do, and name gaps only a person can fill (for example a holding line for a prospect needs a playbook, not the helper). The helper may also append to the folder's CHANGELOG because that folder's AGENTS.md asks for it: mention it. For an interview-style helper (it asks a client questions), a `-z` run is one turn: pass several made-up answers, a document text and one trap (a discount or an early 'we are done') in the same prompt, then read the file it wrote. Promote with `registry.py --approved set-status <slug> production` (flag BEFORE the subcommand) only after his yes to 'was the result right?'; leave the other members in `testing` until each has had its own first task.
- A first real paid run is verified from the vendor's own record (run count and usage through its API), not from the helper's self-report; if the vendor refuses the run (for example a cost cap below its minimum), the brief was wrong, not the helper: leave the helper's cap alone, draft a `-vN-draft.md` with the corrected value, show the worst-case cost change in plain words, and ask for a new yes before re-running.
- Promotion is `registry.py --approved set-status <slug> production` and nothing else. Do not also run `registry.py review <slug>`: it stamps `last_review` with today's date, no script undoes it and the registry may not be hand-edited, so the real review (after three real tasks or seven days) would start with a false record. Run `review` only inside stage 10. Update the hand-over card's Status line after promoting.
- When the promotion question ('was the result right?') gets an answer about something else (a design point, a new idea for the system the helper connects to), it is not a yes: confirm in one line whether it matches the brief's assumption, change no approved brief, leave the helper in `testing`, and ask the promotion question again. If the answer opens a new job (for example a client-facing interviewer inside his CRM), go back to stage 1 for that job with one question at a time, and do not design or build anything until the readiness gate is true; his CRM-to-Hermes connection, if it does not exist yet, is a named Unknown and a later, separately approved step.
- When Robi says a deliverable belongs to a later phase after you already built its tool, restate it as one assumption, keep the tested tool in `briefs/` unwired, and update the helper to refuse that deliverable with a fixed phrase plus a test that expects it. Do not delete the tool.
- Every approved wording rule grows the helper's `SOUL.md`; `check_agent.py` WARNs above about 8,000 characters (a WARN, not a FAIL). Do not rewrite for each change. Tell Robi, and offer one shortening update when no real work is waiting. Measure a draft before showing it: `create_agent.py <draft> --dry-run --update > $TMPDIR/x.txt`, then count the text after `--- SOUL.md preview ---` with `awk` and `wc -c` (it matches the real file size within a character, so run the same count on the archived live brief to calibrate). The `never:` list is printed into SOUL.md as extra lines and repeats rules already in `instructions:`, so cut it to the few items that are not stated elsewhere before trimming real rules.
- A helper told to ask questions first may ask them even when given work to score or when the request is outside its list. Add explicit priority rules before the greeting flow: reject out-of-list work, evaluate given work straight away, and only then run discovery questions.
- For helper-team identity tests, tell the lead helper to list its specialists without starting them or referring to prior delegation budgets; scenario sessions can carry enough context for a model to answer as if a worker task already ran.
- A closing-format rule (an evaluation table, a rubric tick, an options menu) can pass the scenario check yet fail on a short sample. After any wording change, run the live evaluation prompt several times and count how often the required parts appear.
- Real-run tests over 400 seconds time out in the foreground: use `terminal(background=true, notify=true)` and write output to the scratch folder. A helper may judge a request small and skip its workers, so test with a clearly big request that names them.

## Pitfalls from a software-product request (WordPress plugin)

- When Robi asks for a helper that is really a piece of software (a WordPress plugin, an app) with a Hermes helper as its brain, split it plainly: the Hermes helper is the brain, the software is a separate deliverable. A passing `check_agent.py` only proves the brain answers; say so, because it has no site link, Discord link or timer yet. Agent-creator writes only to `briefs/`, so the plugin is designed there first; once the design is approved for a stage, write and test the code there too (`agent-requirements` `references/wordpress-plugin-build-and-test.md`) rather than sending Robi to Claude Code or a coder, which he rejected.
- A site on a host cannot call a Mac at home: design it so Hermes pulls from each site on a schedule, and only urgent alerts go outward from the site (for example a Discord webhook). Confirm the Mac is always on.
- If every scenario FAILs with 'Billing or credits exhausted ... deepseek' (exit 2), the Anthropic route was rate-limited and the run fell back to the Nous fallback model. The helper is fine; wait for the reset and re-run `check_agent.py --scenarios` in the background.

## Pitfalls from a kit-based helper (deck builder)
- When Robi supplies a briefing plus a zip kit, compare the zip with any live copy on disk (`diff -rq`): the live folder may be newer. Build against the live one and say so.
- A client helper works only inside its client folder. A tool kit outside it is reached through a link in that client's `Sources/` (repos stay put). You may not create it: give Robi the exact `ln -s` command and confirm with `ls -la` before the scenario run.
- A helper that only runs a kit's scripts cannot gain new outputs (for example PPTX or PDF) until the kit owner adds the script. Before offering options, probe what the Mac can really do (`ls /Applications`, `which soffice`, `python3 -c 'import pptx'`, `npm ls -g`) so the choices you give are real. Write `briefs/<name>-converter-spec.md` (interface, method suggestion, an acceptance test that renders the output back and compares it with the original, out-of-scope list) plus a `-v2-draft.md` brief. Record Robi's yes in the draft's Status line as conditional ("APPROVED ..., apply only after <script> exists and passes the spec test"), keep the live helper and its production status unchanged, and run `--update` only when the prerequisite is in place; an update earlier would make every task fail at the missing step. When the helper's new step can be missing, put a rule in its instructions to say so and deliver what it can, never to improvise another way.
- When a request pulls two ways (pixel-exact vs editable), say so plainly, offer the real options with their trade-offs (including what the viewer needs, such as installed fonts) and let Robi choose before writing the brief. A picture-based file is exact but not editable; an editable one is close, not identical, and the brief must say so and make the helper say so in every delivery.

## Helpers that turn a source document into another document (invoice, report, deck)

- Ask for a finished sample output AND a real, recent input, and compare them before writing the brief. The sample may hold data the real input lacks (an old invoice listed hours per ticket, while the real report grouped tickets and kept per-ticket hours only in screenshot pages). Show Robi the mismatch, give the real options, and let him choose the rule before the brief.
- Read each PDF with `read_file`, then render pages with `pdftoppm` and look at them: the text layer can scramble table rows, and screenshot pages have no text. The input's own header (name, role, cutoff dates) may already answer "who is this for" and "which period".
- If Robi sends a corrected version of a sample, use it as the template and drop questions that only applied to the wrong one.
- Never store people's pay or bank details in `briefs/` or anywhere in `Agents/`, even when Robi offers to send them one by one. Tell him they go in one private file inside the helper's own folder that he fills in himself after the build; the helper only reads it and never changes it.
- A bare "yes" or "ok" to an either/or question is not an answer, and neither is a short reply that can be read two ways (for example 'I wanted to have the what-it-could-not-check'): restate the choice as one assumption ('I take that to mean you want those gaps closed; tell me if not') and continue with it, or ask again, with `clarify` buttons (include a "wait" option). A `clarify` that comes back cancelled or timed out is unanswered: ask the same question again, as one assumption if he then replies with a bare "yes". If he picks "wait" or "not now", stop, list in one line what is waiting, and do not raise it again unless he does. When several people may use the helper, ask early whether each may see the others' details (it decides the privacy rules and how it is reached).

## Pitfalls from an invoice helper (Drive, Telegram)

- The full recipe (fixed maker program, private people file, Drive robot account, uploader, two PDF readers) is in `agent-requirements` `references/document-in-document-out-helper.md`. Read it before writing the brief; do not rebuild it from memory.
- Before promising a Drive robot account, prove the target is a Shared Drive with a read-only check as the robot (`files.get` shows `driveId`, `drives.list`): a person saying "it is in a shared drive" can be wrong, and a robot cannot write into a personal My Drive folder.
- Google libraries work only with `/usr/bin/python3` on this Mac, with `-W ignore` to silence the Python 3.9 warnings.
- A `boundary` scenario passes only if the answer contains a word like cannot, ask, approval or confirm. When a refusal is correct but worded without them, add a fixed closing phrase to the helper's instructions through an approved update.
- A helper that must attach a file in Telegram, or lives in a group chat: `references/telegram-groups-and-file-delivery.md`.

## Pitfalls from an intake helper (client onboarding)

- A long pasted spec from another chat may not answer the question you asked. Do not build from it; say what it is, check the helper list, and ask which job is being built now.
- When Robi says "research the standard" for a checklist, search a few agency sources, show the groups as a short list, and let him strike items. Keep logins and accounts out of a record that other helpers will read.
- A team helper that serves many clients keeps per-client records in a sub-folder of its own team folder (`Clients/<name>/`), not in each client's folder (house rule).
- `create_agent.py --dry-run` works on a DRAFT brief, so run it before showing the plan to catch build-spec errors.
- A fixed PDF maker in `briefs/` (JSON in, PDF out, `STOP:` on bad input, never overwrites) is the proven pattern. Test good, missing-section, bad-status, password and overwrite cases, then render to PNG and look at it. Put its exact usage (`--schema`, `--out`, `--check-only`) in the brief's instructions, or the helper must guess.
- A deliverable that depends on a later phase (a client PDF after research fills the gaps) must not be produced earlier. Ask when it should appear before wiring it into the helper's instructions.

## Pitfalls from a paid-tool helper (Apify)

- Apify's hosted MCP needs no login only for `search-actors` and `fetch-actor-details`. Run tools (`call-actor`, `get-actor-run`, `get-dataset-items`, `abort-actor-run`) need `headers: Authorization: Bearer ${APIFY_TOKEN}` in the helper's `config.yaml` and the token in its `.env`. Apify adds extra tools such as `get-key-value-store-record`, so `mcp test` shows 7 tools for a 6-name include list: check `mcp list` says '6 selected'.
- The connection cannot restrict WHICH Actor runs. That rule lives only in the helper's instructions (a rule, not a wall). The real walls are the per-run `maxItems` and `maxTotalChargeUsd` in `callOptions` and the monthly limit Robi sets in Apify Billing; read it with the token at `/v2/home/hermes/limits`. Apify rejects `maxTotalChargeUsd` below 0.50: set the brief's cap to 0.50 and hold the real cost down with `maxItems`.
- A real token looks like `apify_api_` plus letters/digits/underscore (about 46 chars). A 92-character value with spaces gave HTTP 401: delete the bad line with `sed -i ''`, and have Robi copy a fresh token.
- A scraped list (Google Maps) finds places, not companies with a stated UAE plan. Say so after the first run; news and announcement research found the better leads.

## When something fails

Say plainly what failed and what it means for Robi, name the likely cause (use the failure table in `hermes-reference`), propose one fix, and ask before applying anything that changes a helper. Never hide a failure, never mark a stage done because it "mostly works", never claim a helper works without a `check_agent.py` run that has no FAIL.

## Pitfalls found when checking a helper with a team (delegation)

- **Long checks:** `check_agent.py --scenarios` can exceed the 420 s terminal limit when a test starts specialists. Run it with `terminal(background=true, notify=true)` and name the Python that has `yaml` (`/usr/bin/python3`): a background shell may pick a Python without it and crash at once with "No module named yaml" (the old report stays on disk, so read the new output file, not the report).
- **Stale registry row after `--update`:** after every update, confirm the registry row matches the brief (`awk` the helper's `toolsets_off`). A check can FAIL on the stale row while the helper itself is right. Fix by re-running `create_agent.py --update --approved` with the same approved brief, never by editing the registry.
- **One-shot runs cap specialists at 2 in total** (`delegation.oneshot_max_children`); a request for 3 is refused whole and the helper falls back to doing it alone. Interactive app and gateway sessions are not capped. Test team behaviour with a request that needs at most 2 specialists, and read the helper's history (`state.db`, `delegate_task` calls) to confirm they ran. The `team` test can PASS on key words while the helper says it did not use the team.
- **Specialists write files unless told not to**, and they read old drafts in `Work/`. Tell the helper to instruct specialists to return text only and use only the sources it passes.

## Pitfalls from a team build (multi-agent-engineer)

- A one-shot call (`-z`) is one turn: the engineer shows a plan and asks; Robi's yes comes in this chat, then run a second call that says he approved. The missing-helper request to agent-creator (`hermes -p agent-creator -z`) works in the background and saves only `*-draft.md` files; read them, set Status APPROVED only after Robi's yes, copy to `<name>.md`, then dry run, `--approved --smoke`, `check_agent.py --scenarios`.
- Members do not start each other: relay the chain by hand (lead, then writer, then reviewer) with one real, fictional task. Without a shared brief, only the lead writes the handover log; the team map and shared brief (`Team/`) cannot be written by the build script or by agent-creator, so say so and ask Robi who places them.
- When Robi cannot judge a practice result (no real project), show him the output text itself and ask only whether it reads clearly; keep practice members in `testing`.

## Pitfalls from a people-assessment / coaching request

- Depth for this class (interview order, scoring, existing dashboard, scanned books, first live session and the rules it exposed): `agent-requirements` `references/assessment-and-coaching-helper.md`. For a conversational helper the first real use is Robi playing a made-up person in the app; check it against the helper's `state.db`, not a `-z` run (section 7 there).
- When Robi says 'you can check here' and pastes only a terminal prompt (a folder name) or a repo URL, the folder is outside `Agents/`: ask for the path and an OK first, then read only (README, example files, schema). A folder name he gives may differ from the real one: search for it with `find` limited to the folders he uses (Desktop, Documents, Downloads, a 'Claude Repository' folder) at `-maxdepth 3`, because `search_files` over the whole home folder dies on macOS permission errors; then confirm with `git remote -v` that it matches his URL. Never open password or `.env` files, and say plainly that they exist.
- Robi's own decisions (for example 'privacy is covered by company policy', 'ignore the existing HR helper') are recorded as his decisions, not argued again. Still say once, in one line, what the AI can and cannot do: it reads words, not feelings, so its output is clues to validate and a person decides.
- A word he uses in a special sense (for example 'duplication' in a list of traits to assess) is asked about in his own terms; never define it for him. A list of traits he gives is read back as a numbered list with any assumed meaning flagged.
- A bare 'yes' to an either/or ('is that right, or should the admin sometimes give background?') is read as the first option and said aloud in one line.
- When Robi's decision replaces a rule you wrote yourself in an earlier update (for example 'start light' becomes 'hard first'), say in one line that it replaces yours, edit the old rule in the draft instead of adding a second one, and fix the same rule in the matching reference so the skill does not keep teaching the old one.
- Helpers that write setup files for a person to approve (a rubric, a story set) create them during test runs, so unapproved drafts of several versions can sit in the helper's `Work/` while it uses the newest. List them in the hand-over card as awaiting his approval and tell him which one is in use.

## Never

- Skip the interview or the approval, or build because Robi is in a hurry.
- See, type, store or log a password or key.
- Create timers, connect outside tools, or message anyone without a separate, explicit OK.
- Edit another helper's instructions, delete a helper, or promote one to `production` without Robi's clear yes.
