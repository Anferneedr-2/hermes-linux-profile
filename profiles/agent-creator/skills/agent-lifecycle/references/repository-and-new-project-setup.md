# Repository index and setting up a new client, project or department

Read this when Robi asks to organize the helper library, make a generic helper, or start a team for a client, a project inside a client, or a department that does not exist yet.

## 1. What counts as generic (the repository)

- Generic = a real role that more than one project could use: a job and a method, no client data. Examples of the class: team lead, writer, reviewer, project manager, HR, accounting, sales.
- A job that exists for one project only is NOT generic, even if it sounds like a role (an invoice maker for one project, a deck builder for one client, a tool manager tied to one client's space). Do not build a generic twin for it; ask Robi once, then record his answer.
- Builders (agent-creator, the team builder) are neither copied nor generic.
- No registry field or script marks a helper generic and none copies one into a project. The interim marker is an index file in `Agents/briefs/` (`GENERIC-HELPERS.md`: table of generic roles with one-line job, brief file, where the live one lives and a note about client data; then builders, project-specific, retired, not-yet-following, open points). Write the first sorting from `registry.py status` and each brief's `description:`, show it to Robi, and write the file only after his yes. Do not move, rename or retire any helper to fit the index.
- When a conflict shows (a brief says it serves four clients, Robi says it is for one), record both in the index as unresolved; do not pick.
- After the index exists, update the team builder through an approved update so it reads the index before any copy and refuses to copy a project-specific helper.

## 2. New client or project folder

- Before claiming "no script does this", run `ls ~/Team-Workspace/Agents/bin` and read the head of each script. `new_client.py` exists: it makes the client folder from `templates/project`, edits the hub README, and ALSO creates default project bots (memory manager, orchestrator, document engineer; Jira admin is optional) from the older workspace design. Those bots have no brief, tests or registry row, and existing clients do not have them.
- `new_client.py` is not one of the scripts agent-creator may run. Never run it; tell Robi what it does and let him decide.
- Whether every client should get default helpers is Robi's decision. Offer the choice with `clarify` buttons (no fixed set; each team only what it needs, recommended; or build the roles properly as generic helpers and copy them into every client). If he does not answer, leave it open and do not assume. His first reaction to "I assume you do not want them" can flip once he hears they are the standard set, so state the facts (what they are, which clients have them, why they exist) before asking.
- If Robi chooses default helpers for every client, they become NEW generic helpers built properly (brief, tests, registry) and copied in by the team builder; they are not made by the old script. Before writing their briefs, check each default role against what exists: an orchestrator (plans and routes work in a project) is the same job as the team lead, so ask once whether they are one helper, and record the answer. Define each remaining role in one plain paragraph and get a yes per role (for example a memory manager keeps the client's `Memory/` notes current and answers only from them, saying "I do not have that" when empty; a document engineer keeps README, CHANGELOG and a `Deliverables/` index, never edits `AGENTS.md` and never moves a file into `Deliverables/` without approval).
- When no approved script gives the client folder, the registry client entry and the `Team/` files, write a request for Robi in `briefs/project-setup-script-request.md`: purpose, numbered behaviour (dry run first, never overwrite, no bots, registry `clients:` entry, `Team/` templates with headings only, standard `Work/` folders, change-log lines, safe to run twice, `--approved` for the real run), acceptance tests, open questions. Do not edit `bin/`.
- Confirm the exact folder name and slug base before writing the request (lowercase letters and numbers).

## 3. Client, project and department are different

- A client has one folder at the workspace root (client agents work only inside it). A project inside a client is a sub-folder of that client, not a second client; confirm that placement with Robi as one assumption.
- A department is a team folder, not a client. `create_agent.py` creates a team folder when the first helper with `placement: team:<Folder>` is built, so a department needs no new script for the folder itself (its `Team/` files still do).
- `create_agent.py` accepts only `client:<ClientFolder>` (a registered client) or `team:<Folder>`; it cannot place a helper in a sub-folder (a project or department inside a client). Say so before Robi settles the layout, and offer the working option: the helpers are placed at the client level, the sub-folder (for example `<Client>/<department>/<team>/`) holds that team's files, and each helper's instructions say to stay inside it. On this Mac that is a rule, not a wall, which is no weaker than the client-folder limit. Sub-folder placement would be a script request for Robi. The script's own "unknown client" error points to `new_client.py`, the old route, so a new client still needs the setup request in section 2.
- Generic helpers need a home folder where Robi can talk to them with no client data and no access to the scripts. `Agents/` holds the scripts, briefs and registry, so it is a poor home; recommend a dedicated team folder (for example `Generic-Helpers/`), settle it as an either/or with `clarify`, and do not build until he names one.
- Before using a folder name Robi gives, `ls ~/Team-Workspace`: a folder with that name may already belong to another helper that serves several clients. Say so and do not touch it.
- Robi may describe the layers in one message (client, project under it, department, team within it). Write them back as a short list of what you understood, mark names you are unsure of (a mis-heard product name) and ask about the one that blocks the next step first.

## 4. Removing a project and everything built for it

CONVENTIONS keep a retired helper's registry row as history, and no `bin/` script deletes a row or a `clients:` entry. A removal is therefore a separate, explicit request from Robi, done in this order, one item at a time with the result shown after each:

1. **Survey first, change nothing.** `grep -n -i <project> registry.yaml`, list `briefs/` for the project's files, and grep the rest of `Agents/` (teams manifest, CHANGELOG, scripts) for references. Report what exists and what will be left behind (team manifest `teams/<Project>.yaml`, the project's own folder, CHANGELOG lines, the engineer's `Work/<Project>/` folder, which agent-creator may not touch).
2. **Files in `briefs/` (test reports, drafts the project produced):** delete only the named files, after confirming that the registry and scripts do not point at them (`*-test-report.md`, `-archive.md` and similar suffixes are ignored by the scripts). Print `DELETED` or `NOT FOUND` per file, then `ls briefs | grep <project>` to prove none are left.
3. **Registry rows and the `clients:` entry:** only after Robi's clear yes to the method. Because no script does it, say so plainly and offer the choice (a one-off script, or a request to add a removal command). The one-off script is written in `$TMPDIR` (never in `Agents/`), imports `registry.py` (`sys.path.insert(0, '.../Agents/bin')`), and for each row calls `R.load()`, checks `status == 'retired'` and `home == <Project>`, removes the row, then `R.save(d)`, which backs up `registry.yaml` first. Remove the `clients:` key last and only when no row still has that home. Run it with `/usr/bin/python3`, then `registry.py sync`, `registry.py status`, `validate_registry.py` (expect 0 errors) and `grep -c -i <project> registry.yaml REGISTRY.md` (expect 0). Delete the script afterwards and give Robi the backup path.
4. **Generic helpers linked to the project:** these are separate. List which generics were added for it (registry rows created around the project's build, `GENERIC-HELPERS.md` rows) and which existing generics only received metadata (`generic: yes`, `definition_id`, `definition_version`, `capabilities`; find them from `*-metadata-fix-notes.md` and `grep -l '^generic: yes' briefs/*.md`). A generic is used by other projects, so remove none without Robi's yes on each one, asked one at a time, and flag any whose brief mentions the project's CRM but is not in its team manifest.
   **When Robi has approved removing the generics and their metadata too** (one request covering everything), still go one item at a time and show each result; never run `check_agent.py` on a live helper during a removal (it overwrites the helper's test report and registry test line and the scenario results cannot be restored). Per generic: (a) `create_agent.py --retire <slug> --approved` (deletes the live profile and its memory, keeps the row), (b) remove its row with the same one-off script pattern (check `status == 'retired'` and its home first), (c) delete its brief, `-draft`, `-prev-archive`, `-vN-archive`, `-test-report` and any `-metadata-fix-notes` files from `briefs/`, one helper per command, then `ls briefs | grep ^<slug>`. Take `R.backup_registry()` before the first row change and report its path.
   - **Metadata lines on older generics:** copy each brief to the scratch folder, remove only the added `generic`, `definition_id`, `definition_version`, `capabilities` block (and its list items) with `patch` anchored on the lines before and after, then `diff` against the copy: the removed-line count must match the fix note (for example 8, 8 and 11) with 0 added lines. A brief of a helper deleted in the same request needs nothing. Delete the matching fix-notes files afterwards.
   - **Index (`GENERIC-HELPERS.md`):** remove the helpers' table rows and change the "Updated" line; leave text dated before the project (the default-set and open-points sections) and say so, asking only if he wants it gone.
   - **Leftovers:** grep `Agents/` (excluding `backups/`) for the project and role names, delete only files you created (fix notes, scratch copies), and list the rest as not removed: CHANGELOG history lines, the project folder, the engineer's files. Close with `validate_registry.py` (0 errors) and tell Robi when the engineer's own files are free to delete.
5. **Files outside `Agents/`** (the engineer's Work briefs, the project folder): never delete them; tell Robi exactly which are his to remove. A team manifest in `teams/` is the engineer's file too: if it has vanished meanwhile, say you did not remove it.
